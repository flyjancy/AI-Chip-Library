## 一句话总结

> 作者主张 AI 加速器的终局是**"带大缓存和 systolic array 的 AI CPU"**：把阵列做大、数值收到 **7 bit 乘法 + 1:2 结构化稀疏**、把 KV cache 通过**稀疏（indexed）注意力**甩到 SSD、网络用**铜互连的 4×4 torus（"donut"）叠便宜路由器（"box"）**、**取消 host 电脑**——用系统性"少堆料"换取 tokens per dollar，并明确承认这需要一支极优秀的软件团队、也明确承认全文缺少实验证据。

## 研究动机与问题定义

### 要解决的核心问题

作者把全文的核心张力写在执行摘要里，这是读全文的关键：

> **"The biggest tension you'll find in this document is between, on one side, maximizing tokens per dollar and, on the other side, grossly overprovisioning your AI chip with collectively extremely expensive and unnecessary features and capacities so that customers will receive something that resembles what they are already using and used to."**

即：**最大化 tokens per dollar vs 为了迎合客户习惯而过度配置**。作者认为后者的每一项单独看都只占成本的一小部分（比如 HBM "只有 20%"），因此每一项都"不值得"改——这正是浪费得以保留的机制。

### 现有方法的三个具体痛点

1. **阵列尺寸的两难**：attention 的 K 维度小（当前通常 16–128），FF 的 K 可以到 8,192。**Google TPU 的阵列大（256×256）→ FF 高效、attention 利用率低；NVIDIA GPU 的阵列小（Blackwell 64×64，面积只有 256×256 的 1/16）→ attention 潜力高、FF 硬件效率低**。两者都是"单一尺寸（mono-sized）"阵列，本质上是 **100% 偏向一侧**，是最不平衡的配置。
2. **大 HBM 是被 KV cache 和权重撑起来的**：作者用一个显式公式算出 KV cache 需要 **4,194 GB**（见下），并认为"AI 产业正在不必要地造成全世界的内存短缺"。
3. **网络被做成 router 拓扑，而 router 天生最多 50% 效率**：因为路由器的平均跳数恒为 2（chip → router → chip），而 torus 可以是 1。

### 明确的适用前提

> **"The recommendations I'm giving in this document assume that you have a most excellent software team that can make this all work ... You will absolutely not have an easy time hiring a software team that can do this."**

作者反复强调：**同一个硬件在好软件和坏软件下的需求可以差 10× 到 100×**，因此"该给芯片配多少带宽/容量"这个问题本身没有脱离软件的答案。

## 核心结构（设计主张与规格）

### 提案摘要（文档第 4 页的 15 条）

1. 设计一颗**传统 CPU**，加额外向量算力与寄存器，**每个核挂一个 systolic array**。
2. 有**软件管理的大 SRAM 缓存（MB 级）**，未使用的部分可自动当 cache 用。
3. **支持所有内存与网络之间的 DMA**，包括 SRAM–network–SRAM；DMA 支持**硬件 8 bit Huffman 压缩/解压**，速度达 HBM/链路速率。
4. **不需要 host 电脑**——芯片本身就是通用 CPU；确保能跑 Linux 与 TensorFlow/PyTorch；另加不带 systolic array 的 scalar core。
5. **不要给芯片配大量 HBM**——靠多芯片装权重。
6. **随芯片提供 SSD**；通过稀疏注意力让 KV cache 落到 SSD。
7. **systolic array 只支持 7 bit 乘法**，不支持 16 bit；累加位宽更宽并饱和。
8. systolic array **对 RHS 支持 1-of-2 稀疏**——简单且带来 2× 吞吐。
9. 主网络是**铜走线的 1D 或 2D torus**；用便宜的定制主板互相"snap"拼接，连接走线；**不用昂贵线缆**。
10. 为芯片写 **XLA 后端**；也支持自定义 kernel 与用标准 C++（含 intrinsic）写的自定义 XLA op。
11. 设计**也能用于训练**，但先聚焦推理。
12–15.（上述各点在正文中展开的原则）

作者对"这不就是 CPU 挂个 systolic array 吗"的直接回应是：**"Yes, that's what I believe."**

### systolic array 的三个维度

作者把 N×K×M 三个维度分开讨论，并给出利用率的核心公式：

- **N（LHS 行数）**：物理上阵列只有 K×M，但要让阵列 100% 利用率需要足够的 LHS 行数来填满 RHS 装载时间。若 LHS 与 RHS 带宽 1:1，则 **N = M**（128×128 阵列需 N=128 行，N=1 时利用率 1/128 ≈ 1%）。放宽带宽比可得：

  ```
  N = M × bw_ratio = M × (LHS bandwidth) / (RHS bandwidth)
  ```

  N 对应 decode attention 的 query 向量数、decode FF 的 batch × 推测 token 数。**降低可用 N 可以降 batch → 降 token latency 与 KV cache**，但要同时提高 HBM 与 SRAM 带宽，代价很高。
- **K（归约维）**：attention 的 K 小 → **限制了大阵列的 K**；FF 的 K 可超 16,000。K 也可以大于 N、M，但这会让向量宽度与 K/M 都不一致，软硬件都复杂化。**K=1024 时 FF 的层内并行度最多 16**（16384/1024）。
- **M（输出维）**：增加 M 近似于两个共享 LHS 的阵列，不如直接放两个阵列；若要增加 M，最好**同时增加 K 与向量宽度**（即做成更大的方形阵列）。

### 数值与稀疏

- **面积/功耗递减效应**：FP32 → FP16（乘法 16 bit、加法 32 bit）→ **BF16**（作者认为这是 Google 相对 NVIDIA 的一次创新优势期）→ FP8（NVIDIA/Arm/Intel 联合发明，**标志 Google 优势期结束**）→ FP4。**"如果量化做得对，推理永远不需要超过 8 bit"**，所以 8 bit 已经足够甚至过剩。
- **作者认为 NVIDIA 支持过多格式（MXFP8/MXFP6/MXFP4/NVFP4）"有点 crazy"**，在 systolic array 内引入显著复杂度，这削弱了"阵列是简单高效结构"的形象。MXFP4 每数 4.25 bit。
- **Google TPU 不支持 FP16 是在省面积**：NVIDIA 为兼容而付了 FP16 的硬件成本，TPU 不必付。这是作者少见的"某方占优"的明确判断。
- **结构化稀疏**：A:B 稀疏（每 B 项最多 A 个非零），NVIDIA 自 Ampere 支持 2:4。收益是 **2× 阵列吞吐 + 接近 2× 的带宽与存储减少（位置需额外 3 bit/4 项）**，面积与功耗只增极少。**稀疏只对权重可用，对激活不可用**，因此 attention 里的激活×激活矩阵乘与 KV cache 都不受益。
- **作者的提案：1:2 稀疏 + 7 bit 整数的单一 8 bit 格式**——第 1 bit 表示非零项在两个位置中的哪一个，剩下 7 bit 是该整数的值。这样就是**一个原生支持"7 bit 稀疏"和"7 bit 稠密"两种格式的 7 bit 乘法器**；稠密时把第 8 位设为 0（有利于压缩）。为了凑满 32 bit 向量寄存器，需把相邻两行打包成一行（8 行填一个 32 bit 寄存器），**行数不是 8 的倍数的矩阵，作者建议"用扔出窗外作为解决方式"**。作者认为 **5 bit 实际够用且比 4 bit 好得多（遗憾 5 不是 2 的幂），7 bit 肯定够**。
- **Google TPU 的 SparseCore 与结构化稀疏无关**：它不含 systolic array、不做矩阵乘，其"sparse"指的是能以更细粒度访问 HBM，用途是 embedding 查表。作者建议："要复刻 SparseCore，不如直接放一个普通 CPU 核。"

### 压缩：lossless 与 lossy 是两件事

- 核心澄清：**lossy 压缩去掉多余精度，lossless 压缩利用数据非均匀分布——两者不同，JPEG 两者都用**（先 lossy 再 Huffman）。作者问："为什么 AI 不这么做？我也不知道为什么。"
- 机制（编码/解码表）：8 bit 整数 → 2^8 = 256 项编码表，输出变长比特模式；解码表 2^10 = 1024 项（最长 10 bit），存原值与编码长度。**关键扩展：编码表可把多个值映射到同一比特模式，于是 Huffman 表同时实现了 lossy**。FP4 全部值 ×2 后可用 8 bit 整数表示，所以**存在一张把 Int8 编码成 FP4 的编码表**。阵列内部与吞吐不变（仍是 8 bit），但通过**改变编解码表就能动态构造 FP4 或任意定制格式**，用于省存储与带宽，并获得 lossless 的额外收益。
- 因此可以**逐层跑自动优化搜索 lossy + lossless 的最佳组合**。压缩可以作用于激活（因此也能作用于 KV cache），变长带来的波动可用**高/低优先级 token**解决（低优先级 token 延后重跑）。
- **落地方式**：做进芯片的 DMA 特性，只配置每个 DMA 是否压缩/解压，对软件基本透明；需要高吞吐但不一定低延迟（因为软件流水化）。**作者明确承认没有量化过这个优化的收益与面积/功耗代价，也没有找到充分的公开研究。**
- **对 TurboQuant 的评价（值得记录）**：Google 的 TurboQuant 号称 ~8× KV cache 压缩，**其基线是每元素 32 bit，因此这个数字"毫无意义"**——8× 意味着降到 4 bit，而 4 bit 早已做到，所以新闻宣传聚焦的部分"甚至不是改进"。**真正的进展（若博客其余部分可信）是不需要重训、精度损失小、甚至不需要校准数据**——这才是有意义的，但媒体报道基本没提。

### 三类工作负载的差异化需求

| | 训练 | prefill | decode |
| --- | --- | --- | --- |
| 目标瓶颈（若软硬件做对） | compute-bound | compute-bound | 希望 compute-bound，**可能做不到** |
| 硬件额外需求 | 高速转置、额外向量算力（Adam 等优化器）、16 bit 数值、更多 op 与融合、更高灵活度 | 大 systolic array | 更小阵列 + 更高带宽 |
| 软件复杂度 | 最高 | 中 | 中高 |

- **训练芯片不建议作为创业公司的第一颗芯片**：训练对软硬件复杂度要求显著更高、单芯片成本更高，而客户是每天出新想法的 AI 研究者，需要极高的软硬件灵活度。**TPUv1 本身就是推理芯片**，所以"跟随 Google/NVIDIA 做训练芯片"不是 Google 的路径。
- **decode 的朴素实现利用率低于 1%**：只有一个 query 向量，矩阵乘的 N=1；上下文窗口百万时每次要拉入百万个 key，32 层就要重复 32 次。
- **两个乘数可以救 decode**：**GQA** 把利用率与 KV 带宽同时改善 128/G 倍（G=8 时 16×），并可顺带加宽 key/query 向量从而**增大 K 维度**；**speculative decoding** 用 4 token 推测再给 4×。**合计 4 × 128/G，G=8 时是 64×**（对应图 1 的示意）。若还结合"非方形阵列降低所需 N"，理论上还能再拿到最后 4× 以填满 256×256。
- **为什么不能取 G=1 或推测 16 token**：G=1 意味着所有注意力头共享一组 key，模型质量显著下降；推测 token 越多，那个"笨 AI"（草稿模型）越可能在 16 token 前就说错（"blurt out pineapple"），算力白费。**两个都是需要权衡的平衡点。**
- **"agent multiplication"（多条并行思维链）是又一个乘数**：4 条链 → key 复用再 4×，等效于给单个用户 4× batch。作者的推论很实用：**这并不让 LPU 无用**——因为你有 16× batch 就可以买 16× 的 LPU 并同样拿到 16× 的单用户吞吐，**LPU 在高价低延迟 token 上仍然领先**；但它会改变经济性（要买的更多，且更便宜的方案可能已经"足够快"）。
- **prefill 与训练没有这个问题**：token 已知，可以全部并行处理，每个 key 读进来后被用数千次。**GQA 在 prefill 的作用是增大 K 维度**（而非 N）。
- **RAG 意味着未来的 token 大部分是 prefill 而非 decode**（因为助手要读网页与数据库），**这使 systolic array 的重要性不降反升**。

### decode/prefill 的聚合与分离

- **默认聚合**：同一芯片同一 kernel 混跑，比例不受管理，可能一颗芯片全在 prefill 而邻居全在 decode。
- **分离（disaggregation）**：prefill 与 decode 放不同芯片（甚至不同种类），需搬 KV cache。好处是软硬件可专门化；也能避免 decode token 被上千个 prefill token 堵住。
- **受管理的聚合（managed aggregation）**：**作者自己造的词，实现上近似于"chunked prefill"**。核心洞察是：**decode 受内存带宽限制、prefill 受阵列算力限制，按正确比例混合可以让两者都满负荷**，同时改善延迟与吞吐。**推论是这类芯片可以不配那么多内存带宽。** 作者把这条列为"bold (read: risky) move"——因为不是所有客户都会这么做。

### HBM 容量：一个显式公式

作者给出 KV cache 容量公式并逐项代入，得到具体数字：

```
2 × batch × layers × seq_length × attention_head_groups × vector_width × element_size × idle_magnification × pipeline_factor
2 ×   64  ×   32   ×  1,000,000  ×          8           ×      128     ×       1 B        ×         1          ×        1
= 4,194 GB
```

关键推论三条：

1. **这只是 KV cache 一项**，而当前 GPU/TPU 只有 100–200 GB HBM，所以**必须跨芯片分布**（层内并行 32 路 → 每芯片 131 GB，正好是 200 GB 级配置的来源）。
2. **权重不是问题**：1000 GB 权重在 32×32 = 1024 芯片上只有 1 GB/芯片。**权重存储被"层内 + 层间"并行都改善；KV cache 只被层内并行改善，不被 pipelining 改善**（见下）。
3. **作者的主张**：用**稀疏检索把 N 从 10^6 降到 10^3（近期 1024 token 用稠密注意力，更早的用检索，落在 SSD 甚至更远处），4194 GB → 4 GB**。于是"一颗 32 bit 芯片只需要 4 GB 内存"（32 bit 指针上限 4 GB），配合大规模并行就能与 100–300 GB HBM 的芯片竞争。**代价是最小安装规模大**（1 TB 模型至少 256 张卡）。
4. **作者对"大 HBM 为什么存在"的解释**：不是技术必需，而是**为了让不擅长部署的客户也能用**——"你最终会为那些在软件上做得更高效、但他们不会那么做的客户，在硬件上做非常昂贵的事"。他认为这也与高利润率有关。

### 并行化（全文最复杂的一章）

**作者列出的三个"反直觉事实"**：

1. **网络带宽是层内并行的限制**——这是 AI 推理需要快网络的原因；**增大网络带宽可以支撑更多层内并行，从而最多把 token latency 减半**。推论：**大 systolic array 是推动更快网络的力量**（因为大阵列需要大 batch，而大 batch 拉高 token latency）。
2. **层间（pipelining）帮助权重存储但不帮助 KV cache 存储**；**层内并行帮助 KV cache 存储**，而它受网络带宽限制。**所以网络带宽与"你需要多少 HBM"直接相关。**
3. **如果芯片速度翻倍，网络也必须翻倍。**

**KV cache 为什么不受 pipelining 帮助（非显然）**：pipelining 让每层的对话数增加 S 倍，所以单芯片每对话的 KV 少了 S 倍，但在飞对话多了 S 倍，**两个 S 相消**。

**四种并行方式的对照表**（作者给的原文对照，整理如下）：

| 方式 | 吞吐 | token latency | 每芯片 HBM | 可靠性 | 网络 | 阵列利用率 |
| --- | --- | --- | --- | --- | --- | --- |
| **duplication（D 份）** | ×D | 无影响 | 无影响 | **改善（唯一一种）** | 基本不变 | 不变（可达 100%） |
| **层间 partial pipeline（S）** | 略小于 ×S | 增加 | 权重 ÷S，KV 不变 | 变差（失败域 ×S） | **关键路径上，极重要** | 降低（永不达 100%） |
| **层间 full pipeline（S）** | ×S | **加倍** | 权重 ÷S，**KV ×2** | 变差 | 只要"够快"就无影响 | 不变（可达 100%） |
| **层内（P）** | — | **降低** | 权重与 KV 都改善 | 变差 | **带宽需求"略多于翻倍"** | 对 FF 可 100% |

- **full pipeline 的机制**：把在飞对话加倍，一半在被计算、一半在被传输，每级交换位置；结果是阵列永不等待网络，**因此层间网络不必那么快**——这是它最重要的价值。
- **层内并行的具体可拆解程度**：attention 可按 128 个 head 拆，但用了 GQA 后最好把同组 head 放同芯片（否则失去 GQA 的 decode 收益），于是只有 G（如 8）路；再把 **KV cache 拆到 2 或数片**（长上下文下可得 4–8 路），**合计可达 ~64 路**。FF 可拆得更多：**256×256 阵列 + 16k 模型向量宽度 → 最多 256 路**，且 prefill/decode 都适用。
- **网络量的精确口径**（for nerds 框）：all-reduce 的每芯片传输量是 **2X(1 − 1/P)**，对大的 P 趋于 2X 且**不随 P 增长**；但**步数随 P 增长，所以每芯片带宽需求仍需大约按 P 增长**。"这就是 AI 芯片带宽需求巨大的一个主要原因。"
- **层间带宽相对层内是"中性"的**（每芯片层间发送 1/P 数据，抵消了 P 倍速度），所以**层内需要远高于层间的带宽**——这意味着**层间传输可以放在慢得多的网络上**。
- **软硬件都依赖 vector width 是坏生意**：作者给出三条论据——① NVIDIA 与 Google 历史上都多次改变向量宽度，硬编码会导致不必要的软硬件重写；② **测试故事**：256×256 tile 的测试需要每个测试手工核对 65,536 个数，若软件对向量宽度参数化，就可以写 2×2 的测试并确信 256×256 也对（**"据我所知今天没有人在用这个想法"**）；③ **FPGA 验证**：参数化的设计可以把 2×2 阵列塞进 FPGA。结论：**"你不需要做两颗芯片，只需要把向量宽度做成符号常量。"**
- **MoE 的动态性问题**：专家利用率不均（"专家 A 懂英语名词，专家 B 懂公元前 405 年蒙古的帽子"）；**120% 负载的专家需要复制成两个各 60% 负载，于是两个都只有 60% 利用率**；高倍数下取整效应减弱（1020% 负载 → 11 片 → 每片 93%）。**不给 token 排队就不可能达到 100% 利用率**（除非用强制的均匀路由，但那会让你的回答质量取决于别人同时在问什么——**作者认为"有些助手真的这么做。Yikes!"**）。作者认为 **MoE 实际实现的利用率远低于 100%，但"我认为可以用更好的软件改善"**。
- **作者对 MoE 的预测**：知识不应主要存在权重里；应该**用层内向量数据库检索把大部分知识移出去**，从而大幅减少权重并提升精度——**这会让 MoE 的收益大幅下降，但 MoE 仍会用，只是专家数很少（4 或 8 个）**。

### 网络拓扑与作者的自提方案

**核心论证：router 天生最多 50% 效率**

作者的公式是：

```
每芯片平均有用带宽 = 链路平均利用率 × 该节点所有链路带宽 / 平均跳数
```

- 单 router 拓扑的**平均跳数恒为 2**（chip→router→chip）；**邻居通信的 torus 平均跳数是 1**。因此 **router 永远是"至少浪费一半"**，而 torus 有潜力 100%。再加"要额外买一台路由器"，经济性比 50% 更差。这条论证的锋利之处在于：**路由器自身不是有用的目的地，所以它的每个端口与全部带宽都是被浪费的**。
- **torus 的代价**是 wrap-around 长链路昂贵（TPUv3 用很长的光缆解决）；**folded torus** 让所有链路长度最多为 2，从而可以用铜走线。
- **Big 3（all-gather / reduce-scatter / all-reduce）在 torus 上都能做到只用邻居通信，因此 100% 效率，约为 router 的两倍**；在 mesh 上只有 torus 的一半速度（与 router 同速）；**ring attention 同理**。**MoE 是"齿轮里的扳手"**——它必须多跳，从而拉高 torus 的平均跳数。作者的结论是：**小 torus（如 4×4×4）对 MoE 仍然合适，大 torus 不合适**（16×16×24 的 v5p torus 上 MoE 平均距离达 14，即使把 24 维拿去并行化也还有 8）。
- **作者的自提方案（"N×4×4"）**：
  - **base：4×4 torus = 16 芯片，称为 donut**；用 N 台**现成便宜路由器**把 N 个 donut 连成 **N×4×4 的"box"**——每台路由器连接各 donut 中相同位置的芯片。N=16 → 256 芯片。
  - **N 维用便宜的低带宽路由器**（远低于 torus 的每链路带宽）；N 维用于层间并行（带宽需求低）与权重装载，**顺带把数据中心网络连接并入 AI 网络**，减少"为装载权重而配置、平时闲置"的浪费。
  - **失败域被限制在 donut 内**（单个 donut 从路由器上消失不影响其余 donut），**效果上类似 Google 的昂贵光交换方案，但用的是便宜的现成路由器**。路由器故障也可通过 torus 绕行（4 个邻居各承担 1/4）。
  - **物理实现**：4 宽的 torus 称为 **ring，做在一块主板上**（分摊主板成本、芯片间距离短）；4 块 ring 板拼成 donut；为了闭合环，**把左边两块 ring 板折到右边两块下面**，从而在右侧近距离闭合（避免 TPUv2/v3 那样的长光缆）。目标是 **chip→connector→chip 全程可用无源铜走线**。
  - 还有一个"给喜欢路由器的人"的变体：自己做 16 端口路由器芯片放在背板，配水冷，把 16 块 ring 板装在一块不太大的背板上（2 cm 间距 → 32 cm）。
- **"多跳浪费"这个术语**是作者强调的：**"我这一生从没听人说过路由器本质上最多只有 50% 效率，所以我认为这一点并不显然。"**
- **带宽数字的不可靠性（作者单列一节）**：GB/s 还是 Gb/s（差 8×）、双向是否已合计、Giga(10^9) 还是 Gibi(2^30)（差 7%）、goodput 还是 line rate、理论值还是实测值。结论是**每个人都得自己跑 benchmark**；而在 co-design 阶段芯片还没交付时，只能靠"跟人把上面 5 点逐个问清楚"。

### co-design 与决策方法

- **规则**：**硬件团队不应在不咨询软件团队的情况下设计任何面向软件的接口**。"任何与性能有关的东西都是面向软件的，任何硬件上限大概也是。"
- **最重要的方法论：必须计入"派生后果（derived consequences）"**。作者列出自己职业生涯中四个被误读的真实 co-design 实验：
  1. **op fusion 的影响**：直接把 XLA 的 fusion 关掉再测，会得到"巨大影响"的数字，但这是**幻想**——如果 XLA 从来不支持 fusion，它根本不会被设计成现在这样（XLA 把很多 op 拆成极小的操作正是因为 fusion 支持强）。**关掉 fusion 得到的其实是一个极糟的系统。**
  2. **需要多少 scalar 算力**：把模拟器里阵列时钟调高看是否被 scalar 卡住。看似是科学实验，但"需要更多 scalar 算力"有派生后果——**编译器团队会去优化 scalar 代码**（可能只是轻微 unroll 就够了）。所以实验暗示要翻倍 scalar 算力时，实际上可能一点都不用改。
  3. **TPU 能不能支持动态 shape**：以当时的 XLA 开发实践看几乎不可能，但**"要支持动态 shape"本身有派生后果**（实践与 API 会为它改变）。结论是**能做，只是麻烦**；更好的反对理由其实是"客户并非那么需要"。
  4. **结构化稀疏是否有吸引力**：把每 4 项里较小的两个置零再看精度，结果很差，于是宣布"不work"。**但从来不存在"它work"或"它不work"，只存在"用这种方法做它work/work"**。
  作者把"省略相关因素"列为同样严重的一类错误，并列出一长串"每个 AI 芯片创业公司都比 Blackwell 快"的可能解释（只报对自己有利的 benchmark、对手的并行被关掉、1:1 对比但一方以 1000 为单位卖、per-chip 快 2× 但价格贵 10×、测 1000 次取最好而对手只测一次、只测不能持续的加速段、只让一个模型 work）。他的结论是一句很强的话：**"Numbers are meaningless. Experiments are meaningless. Data is meaningless. ... It's all bullshit. Unless you understand the context and meaning."**
- **反对"hill climbing"式的 co-design 流程（POR）**：标准做法是"研究→出提案→讨论→定为 Plan Of Record→后续改动按对 POR 的增益决定采纳"。作者指出这在优化里就是 **hill climbing，会卡在局部最优**，而且无人处理。
- **"bloat protects bloat"的数学**：设两个独立的节省方案各把成本从 $1.01 降到 $0.51（各 2×，单独看"不值得"），**两者一起则从 $1.01 变 $0.01（100×）**。原因是"每美元能买多少件"是 **1/x，不是线性**。因此**不能孤立地评估不相关的决策**——每一项节省都让其他节省更有力。作者的结论是 co-design 应该是**跨多维决策组合搜索（combinatorial search）**，而不是 hill climbing，并承认这会复杂到"你很快就会不再信任这个模型"。
- **作者对 co-design 团队的建议**：应由**同时承担其他职责的人**组成（这样才有"价格"与产品的实感），但要有明确交付；全职 co-design 团队也可以，但很难落地。

### 对 NVIDIA GPU 特性的批评

结论句：**"如果把 AI 不需要的昂贵特性从 NVIDIA GPU 里去掉，剩下的大致就是一颗带 systolic array 和高内存带宽的 CPU。所以 GPU 在 AI 上成功是因为 NVIDIA 极其擅长造 GPU 和为它写软件，而不是因为 CUDA 最适合 AI。"**

逐项：

- **kernel 与 warp specialization**：kernel 是图形着色器的遗留物。想同时做计算与网络时（这在高性能部署里是必须的），**CUDA 不能把两个 kernel 复用到同一个 SM**，于是要么牺牲一整个 SM 的 systolic array，要么自己在 kernel 里手写复用。更糟的是 all-reduce 比下一个 kernel 更长时，得手动把它切进多个 kernel。**在 CPU 上这只是起两个线程的事。** 解法是 **megakernel**，而 NVIDIA 为了让它高效不得不加 warp specialization 硬件——**这本质上是"让 GPU 更像 CPU"的笨拙办法**。**TPU 的对应问题不同：它已经像 CPU 一样跑长程序，但硬件没有复用（multiplexing）特性**，所以要在软件里做，XLA 有时能自动完成。
- **path divergence（向量子集）**：GPU 上一个硬件特性，CPU 上可用软件（开销更高）实现。作者认为**对 AI 加速器不值得做成硬件**——"更轻量的向量指令就能达到同样效果"。并给出建议口号：**"Powers of 2 are right, otherwise your code's a blight."**（257 可能比 256 慢一倍。）
- **软件管理的 cache**：这是作者**明确肯定 GPU 的一点**——NVIDIA 同时有自动 cache 和手动 cache（shared memory），**对高性能 AI 而言手动 cache 反而比自动 cache 更方便**，AI CPU 应该两个都有，理想情况默认全部自动、可按需把一部分转为手动。
- **warp scheduling**：本质是"硬件实现的隐藏流水化"，用来让 warp 在等内存时切换。**它不是在 AI 上快的原因，而是要用满 GPU 内存带宽就必须付出的代价**；它是 CUDA 编程模型（warp）的产物、图形遗传的痕迹。**替代品是软件流水化**，后者"更快更便宜"。作者判断：**"这一个特性大概是让 GPU 成为 GPU 而不是 CPU 的最大部分。"**
- **需要 host 电脑**：GPU 与 TPU 都需要 host 来编排 kernel 并处理输入输出，这给系统加了非平凡成本、增大了失败域、增加了一次不必要的数据与命令中转（例如增加 kernel 切换开销）。对"那只是把成本从一处挪到另一处"的反驳：**设备可以比现成 CPU 更专为自己需要而设计，而且两个组件之间存在连接成本**。
- **大量线程与 kernel 切换开销**：每个线程启动时要自己算"我是谁、该做什么"，而所有线程同时在算 →**阵列在这段时间闲置**；kernel 结束时必须等最倒霉的那个线程；硬件还要维护大量线程/ warp 的状态（面积与功耗）。TPU 的对照是**它只有 2 个核、确定性更强**。作者还提到 **TPU 上理论上可做到 zero cycle kernel switching**（若下一个 kernel 已预载），实际会受软件流水化 prologue/epilogue 影响；把前一个 kernel 的 epilogue 与下一个的 prologue 重叠是可行但他当年没做的优化。

### 其他值得记录的技术论点

- **cycle tyranny（作者自造的术语）**：驱动阵列的核必须**每个周期**都准备好 LHS/RHS/输出三组向量，加上读入与 softmax 等可能达 10 个向量操作/周期、向量宽度 256——"这是要在硬件里提供的巨大向量算力，同时在软件上让这个核几乎没有余量做别的事"。作者**知道有一个（不是 TPU 的）芯片项目因为没认真对待这件事而彻底失败：无论怎么编程都无法让阵列满载**。缓解手段：2D 向量寄存器（TPUv2 是 8×128，直接降 8 倍 tyranny）、阵列前后加硬件队列、降低阵列时钟（早期 TPU 的做法），以及作者**没见过有人用过的想法：systolic array DMA**——一条 DMA 直接搬运数千行/列进出阵列（可从 SRAM/HBM/网络/另一个阵列），大幅降低 tyranny，且数据不复用时省掉经寄存器/SRAM 的带宽。代价是需要非标准数据变换时仍要走核。
- **热与 throttling（TPUv3 的实例）**：阵列功耗密度极高，**TPUv3 设计阶段低估了阵列发热**，回片后在 Google 总部出现"令人不快的意外"。补救不是重做芯片，而是硬件团队的一长串缓解措施 + **作者自己写的编译器静态分析方案（内部称 "compiler throttling"，后被他上级的上级指出"Sucks at marketing"，应该叫 Turbo Mode）**——用经验验证的发热模型保证编译器永不生成会危险发热的指令模式，结果**让 TPUv3 能安全地把时钟提高 25%**，部分工作负载拿到完整的 25%。作者自评这个项目对 Google 的经济价值"超过我年薪的 100 倍"。他给的原理性结论是：**最坏情况的数据/指令模式只有"有人在故意搞你"才会出现，所以要为它做冷却方案太贵且对真实客户无益，但也不能忽略它**——否则云上的恶意用户可以一次性摧毁整个空闲 fleet（芯片被烧掉后数据中心会检测故障并自动换新机，"抱歉，马上给你换台机器"）。

## 证据、案例与论证

这份文档**不是实验型材料**，因此这一节按"证据类型与强度"分层列出。

### 作者的一手经验（最强，但是回忆）

| 事件 | 内容 |
| --- | --- |
| **TPUv3 发热与 Turbo Mode** | 阵列发热被低估 → 作者写编译器静态分析 → **允许时钟提高 25%**，部分负载拿到完整 25% |

| **XLA 的 co-design 经历** | 重新设计了 TPUv4 的 DMA 接口（旧接口"需要某种 bit-pattern 博士学位"）、简化了从未被真正使用的内存保护方案、拒绝了一些会被证明"太难编程"的硬件改动、做了覆盖各代 TPU 所有容量/带宽/上限的表格（"收到数千次访问"） |

### 具体数字（可引用，但多数为作者的估算）

- **KV cache 公式与结果**：`2 × 64 × 32 × 1,000,000 × 8 × 128 × 1 B = 4,194 GB`；改用稀疏检索（N=1000）后可降到 **4 GB**。
- **当前 HBM 量级**：NVIDIA Blackwell Ultra **288 GB HBM3e**；当前 GPU/TPU 约 **100–200 GB**。
- **HBM 成本**：**可能约为普通 RAM 的 3×/GB**（公司不公开）；作者提到见过"贵 HBM 占总成本高达 50%"的估计，但明确标注为猜测。
- **阵列尺寸**：TPU **256×256**、NVIDIA Blackwell **64×64**、CPU 上的矩阵单元 **32×32 或更小**；**256×256 比 16×16 大 256 倍**（边长为 2× 则面积为 4×）。
- **稀疏收益**：2:4 稀疏提供 **2× 阵列吞吐**，带宽与存储收益**接近但不等于 2×**（需存 3 bit/4 项的位置）。
- **层内并行上限**：FF 在 16k 向量宽度 + 256×256 阵列下可到 **256 路**；attention 在 GQA 与 KV 拆分合计约 **64 路**；K=1024 时 FF 最多 **16 路**。
- **all-reduce 传输量**：每芯片 **2X(1 − 1/P)**；P 从 2→4 时 1−1/P 从 50%→75%（显著），64→128 时从 98%→99%（不显著）。
- **MoE 负载取整**：**120% → 两片各 60% 利用率；1020% → 11 片各 93%**。
- **Groq LPU（作者给出的外部数据）**：**LPU3 每芯片 500 MB SRAM**；**100B FP8 模型至少需要 200 张 LPU3** 才能装下权重；N 极小（可能 N=1，作者说"找不到具体数字"）；作者据此判断**LPU 没有使用大 systolic array**（"即使它看起来像"，也拿不到大阵列的面积/功耗特性）。
- **MoE 专家数实例**：Mixtral 8×7B（8 个专家、2 个激活，25% 激活）；Llama 4 Maverick（**128 专家，17B 激活 / 400B 总参数，4% 激活**）；Google 曾发布 Switch-C 1.6T（**2048 专家**）。
- **作者引用的 Google TPU 累计投入**：**~$100B**——**但作者明确标注这个数字来自 Gemini**（"I don't know the numbers any longer, but Gemini suggests ~$100B"）。这是全文最需要降级的引用之一。

### 论证性（非实验）结论

- **router 最多 50% 效率**（平均跳数恒为 2 vs torus 的 1）——这是纯逻辑推导，作者承认他自己"一生没听别人说过"。
- **pipelining 不改善 KV cache 存储**（两个 S 相消）——纯推导。
- **bloat protects bloat**（1/x 非线性）——纯数学。
- **大阵列更容易做出有竞争力的芯片**：因为面积占比越来越大的部分（阵列与 cache）比传统 CPU 外围简单，而"CPU 是硬件工程师已经被训练多年怎么做的东西"；软件复杂度不随阵列变大而下降，所以**不该为了省硬件成本而做难编程的结构**。

## 局限性与未来方向

### 作者自己承认的局限（应优先采信）

1. **缺少实验证据**：对反馈中"the science is missing"的回应是——**"我同意这些是我的观点。它们是有依据的观点，也是我认为正确的观点，但做 AI 芯片的人绝对应该自己验证，而不是只信我的话。"** 他并说这份理解"是我本来会用作起点的东西，会随着工作推进以我无法预测的方式改变"。
2. **需要一支极优秀的软件团队**，而且**极难招到**；本文的全部建议都建立在这个前提上。
3. **多处未解决的技术问题**：**1:2 稀疏能否总是可用"我不知道"**；**非对称带宽 torus 与 MoE 的结合"我至今没能想出办法"**（他很想推荐但不能）；稀疏注意力 + 4 GB/chip 的组合需要大量 AI 研究才可能成立。
4. **未量化的优化**：Huffman 压缩做进 DMA 的**收益 vs 面积/功耗代价没有量化**，并声明"据我所知没有充分的公开研究"。
5. **文档刻意少给数字**：作者明确解释这是有意的——他不想给"some numbers"来混淆读者；很多相关数字（如 HBM 售价）超出他的时间、资源与权限范围。

### 需要外部读者额外降级的点

- **`$100B` 的 TPU 累计投入来自 Gemini 的生成内容**，作者自己标注了不确定。不可作为事实引用。
- **HBM 约为普通 RAM 的 3×/GB、HBM 可能占总成本 50%** 均为估算或"见过的估计"；与厂商材料（如本仓库 Memory 目录）的口径不同，**不宜直接相乘使用**（一方是按 GB 的单价，另一方（如 Jim Handy 材料）讲的是 HBM 占用约 3× 的 DDR 晶圆面积——两者是不同量纲，详见"个人点评"）。
- **TPU 不支持 FP16、Google 在数值创新上"落后"、Google"从未全力投入 TPU"** 等判断属于作者的个人视角（他明确说明自己不是 director/VP，"只能从底部报告看起来的样子"），且含个人回忆性质（如与 Patterson 相关的会议记述、与某位高管的一次对话）。
- **GPU 会成为 CPU 的预测是可证伪的**：作者说"最终我们不会用 GPU 做 AI"，同时承认"如果 NVIDIA 保持现在这种出色执行力，他们可能能跑赢这个未来很久"，因此这条预测的**时间尺度未被给出，不可用于任何近期决策**。

### 作者给出的未来方向

- **AI CPU**（带大阵列的通用 CPU）+"取消 host"是明确的终局主张。
- **索引式（稀疏）注意力**：作者认为"所有注意力都应该是稀疏（索引）注意力"，并寄望它把 decode 的带宽需求降到"连 SSD 带宽都够"的程度——**他甚至说这"可能"（！）**。
- **知识的存放位置应从权重转向层内向量数据库检索**，这会削弱 MoE 的收益（专家数降到 4–8）。
- **co-design 应走向跨多维决策的组合搜索**，并把价格与软件决策纳入优化目标。
- **作者对他人论文的回应**：他明确回应了 Yiren Zhao 关于"更多 FLOPs 无用"的论文，承认论点正确（不 compute bound 时加算力只会降利用率），但补充**"把更大的阵列降频到与小的同吞吐，大阵列仍然更高效（直到某个上限）"**，因此**不应该在不需要更多算力时就削减阵列尺寸**，而应在组合搜索里包含"更大但降频的阵列"这个选项。

## 个人点评

- **这篇文章最不可替代的价值是把"数量级"明明白白地算出来，并且是可被反驳的具体断言。** KV cache 的 4,194 GB、router 的 50% 上限、all-reduce 的 2X(1−1/P)、"bloat protects bloat" 的 1/x 非线性、4 GB/chip 的推算——这些即使作者判断错了，你也知道该攻击哪个假设。相比之下，产业里关于"AI 芯片该怎么设计"的大量讨论是定性且不可反驳的。
- **全文最有冲击力的一句话是 decode 的带宽需求可以差 100× 取决于软件**："pretty much everything about how to provision an AI chip depends on the software and you can end up with answers that are 10x or 100x different。" 这句话给整份文档定了一个特殊地位：**它同时既是设计指南，也是对"用 benchmark 选硬件"这件事的根本质疑**。而且他把这个质疑用在了自己身上（"the science is missing"的回应里承认这只是有依据的观点）。
- **"bloat protects bloat" 是全文方法论上最锐利的一节**。把"每个浪费单独看只占 20% 所以都别改"翻译成"每美元能买多少件是 1/x"之后，问题立刻变成一个可以在白板上讨论的数学事实，而不是 motivational 的"我们要有成本意识"。这一条可以直接搬到任何硬件项目的评审会上用。
- **与仓库其他材料可以对照的三处**（但要注意口径）：
  1. **HBM 成本**：本文说 HBM"可能约为普通 RAM 的 3×/GB"；本仓库 Memory 目录的 Jim Handy 材料给的是 **"HBM takes 3X the die area of DDR"**，Micron 材料也独立给出"约 3× 硅面积"。**两个 3× 是不同量纲（单价 vs 面积），不能相乘或互相印证**——但它们在同一量级上指向"HBM 贵得结构性"，这一点可以互相加强。
  2. **Groq**：本文给出 **LPU3 500 MB SRAM、100B FP8 需 ≥200 张卡、N 极小因而"不是真 systolic array"**；本仓库 B5 的 Groq TSP 论文给出的是全 SRAM、容量受限的同一路线。两处独立指向 Groq 路线的核心代价是**容量与"必须买很多卡"的最小安装规模**，这条对照是可用且有力的（注意芯片代际不同，不要直接比对 SRAM 具体容量）。
  3. **Jalapeño（本仓库 B6 第 1 篇）给出的是反向的机制**：Jalapeño 把异构性"放进芯片内部"（同一芯片按 prefill/draft/verify 切换 compute·memory·network 配比），本文把通用性"放进芯片内部"（CPU + 阵列，取消 host）。**两者都反对"多颗分立专用加速器"，但一个靠片内异构、一个靠片内通用**，是同一诊断的两种相反处方，值得并置阅读。
- **最需要警惕的一点**：作者在"该不该相信数字"上写得极其严格（"Numbers are meaningless ... It's all bullshit"），但**他自己也用了无法核实的引用**（`$100B` 来自 Gemini）。这反而印证了他的论点：唯一可靠的做法是自己验证，而这在 co-design 阶段做不到。读这份文档时，凡是带具体价格或行业规模的数字，都应该按"as determined by an undisclosed process"处理；**而他自己的技术推导（跳数、1/x、KV cache 公式）反而是最容易自己复算、最值得采信的部分**。
- **一个具体的、可能被忽略的设计观点值得单独记住**：**"不要把 vector width 硬编码进软硬件"**。他的第二条理由（测试）在工程上极其实用——若软件对向量宽度参数化，可以用 2×2 的测试覆盖 256×256 的行为，否则要手工核对 65,536 个数；若硬件 RTL 也参数化，2×2 阵列能塞进 FPGA 做验证。**这条在不需要多尺寸阵列的项目里也成立**，而且成本近乎为零。
- **作者关于 Turbo Mode 的那段是全文最好的"co-design 值多少钱"的案例**：芯片发热被低估 → 用编译器静态分析约束指令模式 → 时钟提高 25% → 对一笔以百亿美元计的资产实现 25% 的价值。他同时给出了为什么不能"把冷却做到最坏情况"的原理：**最坏情况只有恶意构造才会出现，但忽略它会让云上恶意用户一次性烧掉整个空闲 fleet**。这个论证（throttling 是必需品，不是省钱手段）在很多讨论里是被搞反的。

## 工程化三问总结

### 1. 它解决了什么瓶颈？

- **应用场景**：大规模 AI 推理（decode 为主，兼及 prefill 与训练）的加速器与整机系统设计。目标函数被明确设定为 **tokens per dollar**。
- **被识别的瓶颈有三处，且都是结构性的而非器件性的**：
  1. **阵列尺寸与模型形状的错配**：attention 的 K 小（16–128）、FF 的 K 大（可达 8,192+），而 TPU 与 GPU 都只有"单一尺寸"阵列——**TPU 是 100% FF 取向、GPU 是 100% attention 取向，两者都是最不平衡的配置**。decode 的朴素实现利用率低于 1%，靠 GQA + speculative decoding 只能挽回约 4×128/G（G=8 时 64×）。
  2. **KV cache 驱动的大 HBM**：公式算出 4,194 GB（N=10^6、B=64、L=32、G=8、W=128、S=1 B），而单芯片只有 100–200 GB，于是必须跨芯片分布。作者认为其中大部分是**可避免的**（稀疏检索 → 4 GB），大 HBM 存在的主因是**为了服务不擅长部署的客户**。
  3. **网络的拓扑性浪费**：router 拓扑平均跳数恒为 2 而 torus 可为 1，**router 天生最多 50% 效率**；且 MoE 破坏了 torus 的"只用邻居通信"特性，把大 torus 的平均跳数推高（16×16×24 上 MoE 距离达 14）。
- **证据强度分层（本材料的关键特征）**：**全部为作者的观点、推导与一手经验回忆，无实验、无原型、无实测**。作者本人对此的定性是"the science is missing"，并建议读者自己验证。可独立复算的部分（KV cache 公式、跳数公式、all-reduce 的 2X(1−1/P)、1/x 的非线性）是**逻辑/算术层面可核验的**；涉及价格、行业规模、TPU 历史的数字需按估算或回忆降级（`$100B` 明确是 Gemini 给作者的）。

### 2. 用了什么结构或方法？

- **一种架构主张：AI CPU**——传统 CPU（能跑 Linux 与 TensorFlow/PyTorch）+ 每核一个 systolic array + 大软件管理 SRAM + 少量 HBM + 随附 SSD + 铜走线 torus + **无 host 电脑**。作者的一句话概括是"a CPU with a systolic array attached"。
- **一套数值方案：7 bit 乘法 + 1:2 结构化稀疏的单一 8 bit 格式**（第 1 bit 表示非零位置、7 bit 是值；稠密时置 0 该位），配套"把相邻两行打包、8 行填满 32 bit 寄存器"的 SIMD 处理。
- **一套压缩方案：Huffman 编解码表同时承载 lossless 与 lossy**（编码表允许多值映射同一码字 → 可把 Int8 动态映射成 FP4 或任意定制格式），落到 DMA 上；逐层自动搜索 lossy + lossless 的最优组合。
- **一套内存方案：用稀疏（索引）注意力把小 N 之外的注意力历史转到 SSD 或更远**（N 从 10^6 降到 10^3 → KV cache 从 4,194 GB 到 4 GB），从而允许 4 GB/chip 的设计与大规模并行。
- **一套网络方案：4×4 铜互连 torus（donut） + N×4×4 的便宜路由器盒子（box）**；ring 板做在一块主板上，4 块 ring 折叠加拼成 donut 以近距离闭环绕行；失败域被限制在 donut 内。
- **一套并行化方法论**：区分 duplication / 层间 partial pipeline / 层间 full pipeline / 层内 / MoE 五类的吞吐、延迟、存储、可靠性、网络与利用率影响；并指出**层内带宽需求远高于层间**这一关键不对称。
- **一套工程方法：co-design 中必须计入派生后果、必须识别被省略的相关因素、必须跨多维做组合搜索而不是 hill climbing**。
- **量化策略**：文档本身不涉及把模型量化到具体 bit 宽度的实验，只给出数值格式的硬件成本与建议（7 bit 够用、8 bit 对推理永远够用、"5 bit 通常足够且远好于 4 bit"）。

### 3. 对芯片架构和 RTL 有什么启发？

- **芯片架构层面**：
  1. **阵列应为异构尺寸而非单一尺寸**。作者的处方是**一颗大阵列的 FF 核 + 若干小阵列的 attention 核，同芯片**，并按 OPs（而非核数）做 50/50 平衡。理由是可验证的对比：TPU 是 100% FF 取向、GPU 是 100% attention 取向，"100% 偏向任何一侧都是最不平衡的配置"，所以**任何非 100% 的配比都是改进**（因为没有任何 transformer 只做 attention 或只做 FF）。**注意这也引入了新的设计约束**：必须按你选的 FF:attention 面积比去约束客户的模型形状，且**attention 核与 FF 核同时存在时若不做流水化，pipeline stage 可能翻倍 → KV cache 与延迟上升**；作者给的最优解是**改模型让 attention 与 FF 并行**（同时减半 token latency），但公开模型通常不是这样训练的。
  2. **把 vector width 参数化**（软硬件都做符号常量）。三条理由都可直接落到工程上：跨代向量宽度会变；测试可以用 2×2 覆盖 256×256（否则每个测试要人工核对 65,536 个数）；FPGA 验证只需 2×2 能塞下。**在不需要多尺寸阵列的产品里也应这样做。**
  3. **"cycle tyranny" 是被低估的失败模式**。作者知道有一个真实芯片项目因为驱动核跟不上阵列而**永远无法满载**。可选缓解：2D 向量寄存器（TPUv2 的 8×128 直接降 8 倍）、阵列前后硬件队列、降低阵列时钟、**systolic array DMA**（一次搬运数千行/列进出阵列，可从 SRAM/HBM/网络/另一阵列，避免经寄存器/SRAM 的额外带宽；对"权重直通"与"KV cache 读取"尤其有效，因为推理时这些数据本来就只是被传输）。作者的实现约束是：**需要自定义数据变换的场景仍必须走核，因此不能据此而削减 scalar/vector 算力**。
  4. **网络拓扑应先算"跳数"再选**。核心公式 `有用带宽/芯片 = 链路利用率 × 该节点全部链路带宽 / 平均跳数`，且**单 router 的平均跳数恒为 2**。由此推出 torus 有 2× 优势且不必买路由器；**但 MoE 会破坏这一优势，因此"小 torus 可以、大 torus 不行"**（4×4 随机对距离为 2，≈router 的 1.5；4×4×4 为 3）。作者的自提方案是**用便宜的低带宽路由器把多个小 torus 连起来**，并把"权重装载/DC 网络"与"AI 网络"合并到同一维上，避免为峰值装载配置的带宽平时闲置。
  5. **内存层级设计应以"最小安装规模"为显式约束**。4 GB/chip 的方案要求 1 TB 模型至少 256 卡；这是它的主要代价，也是判断该方案适用场景的第一道闸门。另外，**权重存储同时受益于层内与层间并行，KV cache 只受益于层内并行**——这条直接影响 HBM 容量该按什么口径来定。
  6. **压缩应做在 DMA 上而不是阵列里**：编解码表放在内存与网络通路上，阵列内部与吞吐不变；需要的特性是高吞吐而非低延迟（因为有软件流水化）；DMA 上的 SRAM–network–SRAM 直通尤其重要，否则要用掉大量 HBM 带宽与功耗。
  7. **热必须按"最坏情况由恶意构造产生"来设计防护**：不要试图用冷却覆盖最坏情况（太贵且对真实客户无益），但**必须有能察觉功耗异常并快速自我降频的硬件机制**——TPUv3 的温度反馈太慢，内部可能先被损伤。可行路径是**用编译器静态分析约束指令/数据模式**（TPUv3 借此把时钟提高 25%），或按功耗而非温度做快速反馈。
  8. **host 与 kernel 的取舍应显式评估**：作者认为**取消 host、把 CPU 核放进加速器**可以减少成本、失败域、一次不必要的中转与 kernel 切换开销；但他也承认**重型工具使用（如大规模编译）仍需数据中心里的 CPU**，他的方案是**通过高速链路提供就近的通用 CPU**，而不是重新引入"控制设备的 host"。关于 GPU kernel 那一节的技术判断是：**kernel 是图形遗留，做"计算与网络重叠"时它会成为结构性障碍**，megakernel 与 warp specialization 是"让 GPU 更像 CPU"的补丁。
- **RTL 层面**：可落到实现层的模块包括：
  - **systolic array 乘法器只做 7 bit、累加位宽更宽并饱和**（作者明确建议乘法用 7 bit、加法用更宽位宽）；数值格式要用一套 8 bit 通路支持"7 bit 稀疏"与"7 bit 稠密"两种解释（第 1 bit 作为非零位置指示）。
  - **RHS 侧的 1-of-2 稀疏支持**（作者认为 1:2 比 2:4 硬件更简单，并指出 1:2 可无损转成 2:4，反之不行）。
  - **2D 向量寄存器**（如 8×W）与**阵列前后的硬件队列**，用于缓解 cycle tyranny。
  - **systolic array DMA**：需定义"跳过寄存器/SRAM 直接往返阵列"的数据通路，支持源/目的为 SRAM、HBM、网络、或另一阵列（可带向量加法）。
  - **DMA 上的 Huffman 编解码表引擎**（编码表 2^8 项、解码表约 2^10 项，含编码长度字段），要求达到 HBM 与链路速率。
  - **软件可管理 SRAM cache**：默认全自动、可按需把一部分转为手动（作者明确以 NVIDIA shared memory 为正面样板）。
  - **多核异构布局**：一部分核带阵列、一部分不带（用于 OS/Python 驱动、all-reduce 等网络算法、RAG/层内检索、输入流水线），从而把中断与 OS 杂务隔离在不含阵列的核上。
  - **片内 CPU 核 + Linux-capable 通路**（作者建议 VLIW 以降低每 scalar 核的面积与功耗，理由是 AI 代码分支少且通常不依赖数据）。
  - **快速的功耗/降频反馈机制**（不是基于滞后的温度）。
  - **跨芯片/跨核的 SRAM→SRAM DMA，绕过 HBM**（否则网络原语会消耗大量 HBM 带宽与功耗，并增加延迟）。
  上述模块的动机均来自作者描述，**但文档没有给出任何面积、功耗、时序或 SRAM 容量的量化预算**——它明确不提供数字（作者说这是刻意为之），因此这些模块的成本必须由实现方自行评估。
- **明确标注为推断的边界**：第 1 问的全部内容（瓶颈与数字）来自作者的主张与推导，**无实验证据**；第 2 问是作者的设计主张，**未实现、未流片、未验证**。第 3 问的架构与 RTL 内容为工程推断，作者本人也声明"做 AI 芯片的人绝对应该自己验证"。文档中明确未提供的量值包括：Huffman DMA 的收益/面积/功耗权衡、1:2 稀疏能否普遍可用、预测命中率类指标（该文档不涉及预测器）、非对称 torus 与 MoE 的可行方案、以及**所有真实的成本与价格数据**（HBM 售价、自研芯片成本、网络设备成本）——这些均为 `TBD`。
