## 一句话总结

> Groq 把单芯片 TSP 的「静态调度 + 确定性执行」推到整个集群：TSP 既当端点又当交换机，用软件调度的 Dragonfly 拓扑（每 TSP 4 条全局链路 × 25 Gbps）把系统扩到 **10,440 个 TSP、>2 TB 全局 SRAM、端到端延迟 <3 µs**，代价是网络完全放弃动态仲裁、背压与虚通道，改用 FEC + 推理重放来处理错误。

## 研究动机与问题定义

- **要解决的核心问题**：HPC/ML 系统历来被划分为 capability 系统（强扩展，最小化单个问题执行时间）与 capacity 系统（弱扩展，增大吞吐），两者的通信需求不同。训练常需要数据并行（弱扩展）、推理用流水线模型并行（强扩展），而**同一个系统要同时服务这两种模式**，要求网络既有高对分带宽又有低端到端延迟。
- **现有方法的不足**：常规 CPU/GPU 多处理器中内存与网络资源由各处理单元**动态共享**，这是非确定性的来源。幻灯片图 1（第 568 页）把"会造成内存与网络引用重排的非确定性来源"标红。间接网络（如 fat-tree）需要中间交换机/router，而**动态仲裁与排队本身引入非确定性**。作者引出的设计目标是：**直接网络**（每个 router 都挂端点）并把端点与 router 合并成"glueless"多处理器——即 TSP 自己既是处理端点又是网络交换机。
- **切入角度**：把单芯片 TSP 已有的**静态调度、确定性数据通路**扩展到整网。既然所有指令的延迟在编译期已知并暴露给编译器，那么**网络注入时刻与到达时刻也可以静态解出**，于是就可以取消硬件路由与流控。

## 核心方法

### 系统组织与拓扑

- **打包层级（第 569 页）**：4U 机箱装 8 个 TSP 称为一个 **node**；每个 node 有 **28 条内部 C2C 线缆**把 8 个 TSP 两两全互连（7 条 local link 接 7 个同 node 同伴）。每个 node 用到的 60 条线缆中有 44 条是短距电缆，占 73%。
- **链路带宽的划分**：每个 TSP 的 pin 带宽被分成 **7 条 local link + 4 条 global link**。每个 TSP 的 4 条全局链路合起来构成一个 **32 虚拟端口的高基数 router**，作为 Dragonfly 的一个 group 单元。
- **C2C 链路**：4 条 lane 的低摆幅差分信号，理论最高 30 Gbps（一般工况统一跑 **25 Gbps**），4 lane 合起来 **100 Gbps**。node 内最长线缆 0.75 m，机架内 <2 m 用 QSFP 铜缆，跨机架才用有源光模块。
- **规模阶梯（第 570 页）**：
  - **33 个 node = 264 个 TSP**，node 之间全互连，形成 **3 跳**最小路由拓扑，合并 **56 GiB** 全局 SRAM。
  - **一个 rack = 9 个 node = 72 个 TSP**，用每 TSP 的 4 条 global link 共 **32 × 9 = 288 个全局端口**。把其中 **144 个端口**用于机架内 9 个 node 的**双连接**（提供 2× 内部 speedup），另外 **144 个端口**接其它机架。
  - **最大配置 145 个机架 × 72 = 10,440 个 TSP**，直径至多 5 跳（源机架内 2 跳 + 1 全局跳 + 目的机架内 2 跳）。摘要给出的口径是：>2 TB 全局内存、端到端系统延迟 <3 µs。

### 确定性如何跨芯片维持（第 570–572 页）

多 TSP 系统靠三个机制建立与维持同步：

1. **Hardware aligned counter（HAC）**：每个 TSP 维护一个自由运行的 HAC，溢出周期很短（<256 周期，也称 epoch）。两个由点到点 C2C 链路相连的 TSP 互发 HAC 值，反射回来与本地 HAC 比较即得链路延迟（模 HAC 周期）。重复直到延迟均值与方差落入系统容差。收敛后两端建立 **parent/child** 关系，parent 的 HAC 作为参考周期性地发给 child，child 比较 `HAC0 + L` 与 `HAC1` 并受限速率地调整 `HAC1`。扩展到多跳靠**生成树**分发共同 HAC 参考时间。
2. **初始程序对齐**：`DESKEW` 指令让某个功能单元暂停发射后续指令，直到下一次 HAC 溢出（epoch 边界）。`TRANSMIT` 在 epoch 边界发出向量，child 侧的 `RECV` 在下一个 epoch 边界消费，随后两端各自发 `NOTIFY` 开始同步计算。多跳时同步开销为 $(\lfloor L/\text{period}\rfloor + 1)\times h$ 个周期（$h$ 为生成树高度），**只在分布式推理开始时发生一次**。
3. **运行时重同步**：`RUNTIME_DESKEW t` 让 TSP 延迟 $t \pm \delta t$，用于补偿长时间运行中的时钟漂移（约 1 个 epoch 的开销）。

**Table 1（ISA 支持，第 571 页）**：`HAC`（硬件对齐计数器）、`SAC`（软件对齐计数器）、`SYNC`（片内暂停指令）、`NOTIFY`（片内全局信号，通知功能单元恢复执行）、`DESKEW`（暂停至 HAC 溢出）、`TRANSMIT`（通过 C2C 链路向 child 发通知）、`RUNTIME_DESKEW t`（延迟 TSP $t\pm\delta t$）。

### 软件调度网络（Software-Scheduled Networking, SSN，第 572–575 页）

- **Scheduled, not routed**：路由不由硬件查表决定，而由编译器编排源端与目的端的一串 send/recv 指令。给定全局时空信息，编译器消除共享输出端口的冲突。示例：TSP A 与 B 同时发给 D 会争用 B→D 链路；硬件自适应路由会撞上拥塞再回退并产生背压，而 SSN 在编译期就选好路径。
- **通信模型**：常规网络的远程事务需要"请求 + 应答"两段（图 9a）；SSN 因为知道何时该发 reply，**省掉请求这一半的网络请求**，数据被"推"向将要消费它的 TSP（图 9b）。从编程模型看，张量来自本地还是远端内存无关紧要。
- **确定性负载均衡**：用 Dragonfly 的路径多样性，**非最小路由**把张量的 320 B 向量分散到源到目的的 C2C 链路上。与传统硬件 Dragonfly 不同，这里的"router"就是端点，注入带宽不再受限而是受交换机带宽限制，因此非最小路由是**带宽感知**的。分析（图 10）表明：**消息小于 8 kB 时非最小路由无收益**；更大消息收益随消息规模与可用非最小路径数增加。切换点取决于消息大小、非最小路径数与单跳延迟。
- **流控**：网络**禁止动态仲裁**（会引入非确定性），也没有常规排队缓冲，只在 C2C 逻辑与 TSP 核心的时钟边界处有很浅的缓冲。**不使用虚通道（VC）**。流控单元（flit）是**向量**：320 B。接收 TSP 能立即向下一跳转发，因此可用 virtual cut-through。目标是 $2.5\%$ 的编码开销（图 11：320 B 向量封装成 328 B，效率 97.5%，含 8 B 的 tail/body/header flit 与 End/Start/Type/Sync 字段）。
- **前向纠错（FEC）**：常规点到点链路（如 PCIe）用链路层重传，但重传会改变包的预期到达时刻，破坏全局同步。因此**每条链路都用 FEC 就地纠正单比特错误、检测不可纠正的突发错误**；关键错误触发运行时的"推理重放"（software replay）以判断是暂时性还是需要更换线缆/电源/TSP 卡。
- **可靠性策略**：N+1 冗余，例如 33 个 node 中用 1 个作备件（开销从 11% 降到 3%，余 32 个 node = 256 TSP 用于计算）。

### 工作负载映射

- **单芯片矩阵分解**：编译器把一个矩阵乘分解为 $[1\times K]\times[K\times 320]$ 子运算，FP16 时 $K=160$、int8 时 $K=320$；**TSP 每周期能跑两个 FP16 或四个 int8 子运算**。
- **多 TSP 分解（第 575–576 页）**：两种策略——**列切分**（把第二个矩阵按列等分，结果拼接，不需要大规模归约）与**行切分**（把第二个矩阵按行等分、第一个矩阵列切分，最后对部分积矩阵归约）。示例 $[800\times32576]\times[32576\times8192]$：先按列切成 8 份，再按行切成 $N=[1..13]$ 份，node 内 8 个 TSP 归约出一份 $[800\times(8192/8)]$ 结果，再跨 node 归约拼接成 $[800\times8192]$。
- **输入带宽的方向敏感性**：$[100000\times100000]$ 的权重矩阵，若 $K\times320$ 瓦片按**列主序**载入需要约 **570 GB/s** 的进片带宽才能维持计算吞吐；按**行主序**遍历则只需 **3.7 GB/s**，远在 16-lane PCIe Gen4 的通道能力之内。图 15 的结果假设输入按最小化注入量的顺序经 PCIe 流式载入。

## 实验与结果

### 实验设置

- **单芯片**：TSP 运行在 **900 MHz**，PCIe Gen4 ×16 主机接口。
- **对照**：Nvidia A100。A100 的 AllReduce 结果测自 8×A100 系统（每 GPU 300 GB/s NVLink，经 NVSwitch 互连），取自 nccl-tests。
- **确定性复现性测试**：在 GroqNode 内 4 个 TSP 上跑 BERT-Large 单次推理 **24,240 次**，用 SQuAD 1.1 dev 数据集。

### 主要结果

**单芯片矩阵乘利用率（图 13，第 575 页）**

对 $[2304\times4096]\times[4096\times N]$（$N=[1376..3500]$，取自已发表的配置），TSP 的**利用率在整个 N 区间稳定在 0.9–1.0**（论文正文的说法是"at least 80% utilization consistently"），A100 的利用率从约 0.5 升到约 0.7，并在 $N\approx 3300$ 附近出现一次明显下折。

**分布式矩阵乘（图 14，第 575 页）**

对 $[800\times32576]\times[32576\times8192]$：

- **延迟随 TSP 数下降**：8 个 TSP 时约 330 µs，16 个时降到约 150 µs，继续增加则平缓收敛到约 120 µs（100 个 TSP）。
- **吞吐随 TSP 数线性上升**：从 8 个 TSP 的约 500 FP16 TFlops 升到 100 个 TSP 的约 13,000 FP16 TFlops（约 130 TFlops/TSP），利用率曲线保持在接近 1.00。

**跨集群规模吞吐（图 15，第 576 页）**

FP16 TFlops 对矩阵尺寸 N（$2\times10^5$ 到 $6\times10^5$）：

| 集群规模 | 吞吐区间（读数近似） |
| --- | ---: |
| 100 TSPs | 约 10,000–11,000 TFlops |
| 200 TSPs | 约 24,000–30,000 TFlops |
| 300 TSPs | 约 33,000–42,000 TFlops |

**8 路 AllReduce（图 16，第 576 页）**

三条曲线：Nvidia A100（实测）、**归一化 A100**（把 A100 的总 pin 带宽归一化到单个 TSP 的 pin 带宽后的假设性能）、Groq。论文的结论是：Groq 在**细粒度通信**上优于 A100，随张量增大两者收敛（Groq 匹配 A100）；归因是共享内存语义需要 mutex/flag 加 memory fence 来保证顺序一致性，而 Groq 因为编译器掌握内存引用与全局时间的全序，**不需要额外的 flag 来通知消费者**。

**BERT-Large 延迟分布（图 17，第 577 页）**

24,240 次运行的延迟直方图（5 µs 分箱）：**99% 的推理在 1225 µs 内返回，全部在 1300 µs 内返回**。编译器给出的估计延迟与实测在多数情况下相差 **<2%**；偏差与方差主要来自 PCIe 输入输出传输的调用时间。BERT-Base 在单 TSP 上也有类似关系。

**BERT 的线性扩展（图 18，第 577 页）**

把模型规模从 6 个 encoder 扩到 24、48、96 个，分别在 1、4、8、16 个 TSP 上运行，**实测吞吐（TOPs）与器件数成正比**——例如用 4 个 TSP 得到相对单 TSP 的 4× 吞吐。

**Cholesky 分解（图 19，第 577–578 页）**

- 矩阵按 **block-cyclic 分布**，每个 TSP 320 行。
- 并行执行时间正比于 $p^3$（$p\times p$ 输入矩阵），实测**净加速比 1.2×、1.4×、1.5×**（对应 2、4、8 个 TSP）。
- 吞吐从 **4 TSP 的 14.9 FP16 TFlops** 提升到 **8 TSP 的 22.4 FP16 TFlops**，相对已知最好结果 [16] 有 **3× 实测吞吐**。
- 关键实现细节：Cholesky 的向量操作（含自定义的倒数平方根近似 `rsqrt`）全部映射到向量处理单元上"单次穿越"（single fly-by）完成，数据在矩阵单元与向量单元之间交替流动。

**AllReduce 的最坏情形延迟（第 577 页）**

256-TSP Dragonfly 的最坏情况只用 **3 跳**，单跳流水网络延迟 **722 ns**，因此全网 all-reduce 的网络延迟为 $722\ \text{ns}\times 3 = 2166\ \text{ns} \approx 2.1\ \mu\text{s}$。三级分层 all-reduce：node 内 8 路全互连为第一级，node 间 4 条全局链路为第二级，目的 node 内 8 路全互连为末级。

### 编译器优化的作用（图 20，第 578 页）

4-TSP 系统跑 BERT-Large 的时钟周期分解，分四类：Compute only、Compute and C2C（重叠）、C2C only、Idling。

- **(a) 未优化编译器**：只按 FLOPs 均衡负载，TSP2/TSP3 出现大块 idle。
- **(b) 优化编译器**：显式考虑数据搬移与 TSP 的空间组织，idle 大幅减少。
- 结果：**实测吞吐提升约 26%**。这一页说明在这套架构里"按算力均衡"是不够的，必须把通信时间一起纳入调度。

## 局限性与未来方向

- **最关键的一处对比不成立**：第 576 页那段"相对 432 个 V100 的集群，我们能做到 100× 以上的 FP16 吞吐"是有问题的——432 个 V100 的数字是**约 2800 fp64 TFlops 的峰值**，而 TSP 的数字是 **FP16**。论文自己写下了一句"V100 GPU cluster results using FP16 data are not publicly known, however, despite differences in precision the TSP speedup is significant"，即承认 FP16 的 V100 数据不可得却仍要给出倍数。用 FP16 对 fp64 峰值宣称 100×，无论数值如何都不构成有效比较，这条结论不应引用。
- **图 15 的读数跨越 2 个数量级却无误差说明**：300 TSPs 的曲线在 N 较大时出现约 42,000 与约 33,000 两个量级的明显波动，论文未解释波动来源，也未给测量次数或方差。
- **AllReduce 对比中有一条曲线是假设值**：图 16 中的 "Normalized A100 perf" 并非实测，而是把 A100 的总 pin 带宽按 TSP 的 pin 带宽做归一化后的假设结果。论文对此是标注清楚的，但引用时若不区分，很容易把归一化假设当成测量结果。
- **第 5.2 节的带宽论证依赖一个理想假设**：$[100000\times100000]$ 权重矩阵在行主序下只需 3.7 GB/s，这个结论成立的前提是"输入矩阵按最小化注入量的顺序经 PCIe 流式载入"。论文明确写了这一假设（"we are assuming input matrices are streamed over PCIe in the order that minimizes the injected data volume"），但这意味着实际模型的数据布局必须与编译器协商一致，不是自动获得的。
- **规模与可靠性直接耦合，但代价未量化**：N+1 冗余下 33 个 node 留 1 个备件，开销从 11% 降到 3%。论文未给出故障率模型、重放（replay）的频率与重放一次推理的时间开销，也未给 FEC 的编码强度与纠错能力。
- **对动态/不规则负载的适用性未讨论**：这套设计把动态仲裁、背压、虚通道全部移除，依赖编译期静态调度。5.6 节的 traffic pattern 讨论也假设"张量流是 ML 模型与切分方式涌现出来的属性"。对于分支、稀疏或运行时数据相关的通信（如 MoE 的动态路由、投机解码的动态长度），静态调度如何应对，论文未涉及。
- **未来方向**：本论文是一篇系统描述性工作，未设独立的 future work 章节。从 5.2 节的讨论看，作者把"切分方案随模型维度变化而不同"（结果矩阵小时行切分更好、大时列切分更好）留给了编译器，这暗示后续工作的重心是自动选切分策略。

## 个人点评

- **这是"用确定性换效率"最彻底的一份工程实现**。多数架构会保留硬件路由、虚通道与背压作为通用性保障，Groq 的选择是把它们全部删掉，改由编译器承担路由决策、流控节拍、甚至死锁避免（论文明确说软件调度下循环依赖仍可能发生，但因为没有"持有资源再去请求另一资源"的行为，死锁的根因不复存在）。为了让这个赌注成立，他们必须在三个层面把非确定性逐个消掉：时钟层用 HAC + DESKEW + RUNTIME_DESKEW 建立全局时间参考；链路层用 FEC 取代重传（因为重传会改变包的到达时刻）；网络层用编译期编排取代动态仲裁。这个"每一层都必须确定性"的链条是全文最有价值的部分。
- **Table 2 是整篇论文最有说服力的证据**。7 条 node 内 C2C 链路在 10 万次迭代下，延迟均值落在 216.3–217.4 个周期之间，标准差 2.6–2.9，min/max 跨度 209–228 周期。这意味着链路延迟可以在编译期被当作近似常数使用——整个静态调度方案就建立在这组数字上。与之呼应的是图 17：编译器估计的延迟与实测在多数情况下相差 <2%，99% 的推理在 1225 µs 内返回。把"估计与实测的偏差"作为核心指标来报告，在加速器论文里是很少见的做法，也正是这套架构的卖点所在。
- **工程细节的可信度高于性能对比的可信度**。图 11 的 320/328 = 97.5% 编码效率、"省掉请求腿"的通信模型、非最小路由在 <8 kB 无收益的切换点、Cholesky 把 `rsqrt` 等向量操作放进 single fly-by——这些都是可以复现、可以对账的设计细节。反过来，100× vs V100 那段用 FP16 对 fp64 峰值做比较，以及图 15 里 300 TSP 曲线的大幅波动无说明，是这篇论文最应该被忽略的两处。
- **一个容易被忽略的洞察在图 20**。同样跑 BERT-Large 在 4 个 TSP 上，仅按 FLOPs 均衡负载的编译器与显式考虑数据搬移的编译器之间差 **26%** 的实测吞吐。这说明在这类"端点即交换机"的架构里，通信不是需要被隐藏的额外开销，而是与计算同等级的调度对象。图 15 里那个 570 GB/s vs 3.7 GB/s 的对比（列主序 vs 行主序载入同一个十万阶权重矩阵）是同一件事的另一个证据：数据布局与调度策略可以直接改变两个数量级的带宽需求。

## 工程化三问总结

### 1. 它解决了什么瓶颈？

- **应用场景与核心瓶颈**：大规模 ML 系统的 scale-out 互连。瓶颈是常规多处理器的资源**动态共享**引入非确定性，使得编译器无法对跨芯片的数据搬移做静态规划。系统的目标是最坏情形 5 跳（最大配置）或 3 跳（264 TSP）内的全网通信，并支持 10,440 个 TSP、>2 TB 全局 SRAM、<3 µs 端到端延迟（摘要）。
- **现有方法为何不足**：间接网络（fat-tree）需要中间交换机，动态仲裁与排队本身产生非确定性（第 569 页）；链路层重传（如 PCIe）会改变包的预期到达时刻，破坏全局同步（第 574 页）；共享内存语义下的一致视图需要 mutex/flag 加 memory fence，多一次请求腿与额外的同步开销（第 573、576 页）。
- **论文证据的分层**：
  - **可复现的机制性证据**：Table 2 的 7 条链路延迟特征（10 万次迭代，均值 216.3–217.4 周期、std 2.6–2.9）；图 11 的 320/328 = 97.5% 编码效率；图 17 的 24,240 次 BERT-Large 实测延迟分布（99% < 1225 µs，全部 < 1300 µs，编译器估计与实测偏差 <2%）；图 12 到图 20 的编译器与运行时结构。
  - **实测性能**：图 13 的 TSP 利用率（0.9–1.0 平坦）；图 14 的延迟从约 330 µs（8 TSP）降到约 120 µs（100 TSP）、吞吐从约 500 升到约 13,000 FP16 TFlops；图 18 的 BERT 线性扩展；Cholesky 的 14.9→22.4 FP16 TFlops 与 3× 对比已知最好结果；图 20 的 26% 吞吐提升。
  - **需要剔除或降级的**：100× vs 432 V100 的 FP16/FP64 错位比较（第 576 页，论文自身承认数据不可得）；图 15 中无误差说明的大幅波动；图 16 中 "Normalized A100 perf" 为带宽归一化假设值；第 5.2 节 3.7 GB/s 的结论依赖"按最优顺序流式载入"这一前提。

### 2. 用了什么结构或训练方法？

- **整体结构与数据流**：TSP 既是处理端点又是网络交换机（"glueless" 多处理器）。打包层级为 chip → PCIe 卡 → 8-TSP node（4U）→ 9-node rack（72 TSP）→ 最多 145 机架（10,440 TSP）。每 TSP 的 pin 带宽分为 7 条 local link（node 内 8 个 TSP 全互连，28 条线缆）与 4 条 global link（4×25 Gbps = 100 Gbps）；node 的 4 条 global link 合起来构成 32 虚拟端口的高基数 router，作为 Dragonfly 的 group。
- **关键机制**：
  1. **HAC + DESKEW + RUNTIME_DESKEW**：用 <256 周期溢出的硬件对齐计数器建立全局时间参考，用 DESKEW 指令把指令发射对齐到 epoch 边界，用 RUNTIME_DESKEW 补偿时钟漂移。
  2. **软件调度网络（SSN）**：编译期决定路径与注入时刻，取消硬件路由表、动态仲裁、排队缓冲与虚通道；通信模型省掉请求腿（push 而非 request-reply）。
  3. **确定性负载均衡**：用非最小路由把 320 B 向量分散到多条 C2C 链路，切换点在约 8 kB。
  4. **向量作为 flit**：320 B 向量是流控单元，封装开销 2.5%，支持 virtual cut-through。
  5. **FEC 取代链路重传**：就地纠正单比特错误、检测突发错误，关键错误触发推理重放。
- **量化策略**：FP16 时 $K=160$、int8 时 $K=320$；单周期可执行 2 个 FP16 或 4 个 int8 子运算。TSP 有 220 MiB 片上 SRAM 作参数与指令存储，全局内存是**逻辑共享、物理分布**的片上 SRAM。

### 3. 对芯片架构和 RTL 有什么启发？

- **芯片架构**：四条。第一，**"端点即交换机"消除了注入带宽上限**——论文指出在 SSN 里注入带宽不再受注入通道限制，而受交换机/router 带宽限制，因此非最小路由必须是带宽感知的（第 573 页）。这是把 router 做进端点后带来的架构性质变化，值得在任何 scale-out 加速器中重新推导。第二，**路由与流控决策上移到编译器，会反过来要求硬件暴露全部架构可见状态**（第 570 页：所有 SRAM 与 stream register），这是一条很强的接口契约：可编译性以牺牲硬件自主性为代价。第三，**FEC 而非重传**的选择是由确定性需求逼出来的——重传改变到达时刻，因此在任何需要跨 die/跨卡时间对齐的架构里，链路层重传都是不可用的，必须靠前向纠错。第四，**确定性负载均衡替代自适应路由**：常规硬件 Dragonfly 依赖 FIFO 深度或发送 credit 做逐包决策，而这里用张量的物理数据量 $H\times W\times C$ 决定分散到几条链路。这条"用张量形状而非拥塞信息做决策"的思路，对任何把粗粒度张量当传输单位的架构都适用。
- **RTL**：可落到实现层的模块包括：HAC 计数器与溢出/epoch 逻辑（<256 周期）；DESKEW / RUNTIME_DESKEW / SYNC / NOTIFY / TRANSMIT 指令的执行路径与暂停—恢复控制；链路延迟测量与 parent/child HAC 对齐的状态机（含受限速率的 HAC1 调整）；320 B 向量的封装/解封（8 B flit、Start/End/Type/Sync 字段、2.5% 开销）；C2C 收发逻辑与 virtual cut-through 转发通路；每链路的 FEC 编解码器；TSP 内的 memory/data path/instruction buffer 的 SECDED 校验；以及编译器可见状态的暴露接口。需要强调的两点约束：**没有虚通道与动态仲裁**意味着不需要 VC 分配器与信用管理逻辑，这部分面积被省掉了（论文未给面积数据，为推断）；**只在 C2C 逻辑与核心的时钟边界有浅缓冲**，因此 buffer 的深度与背压被严格限制（论文未给具体深度，`TBD`）。
- **推断边界**：第 1 问的机制性证据（Table 2、图 11、图 17）属论文实测；性能证据（图 13–20）属论文实验但需剔除 100× vs V100 那一条并按第 5.2 节前提降级；第 2 问的结构与机制为论文直接内容；第 3 问的芯片架构与 RTL 内容为工程推断。论文中未提供的量值——各级 buffer 深度、FEC 编码强度与纠错能力、故障率与重放开销、芯片面积与功耗分解、以及动态/不规则通信负载下的可行性——均 `TBD`。
