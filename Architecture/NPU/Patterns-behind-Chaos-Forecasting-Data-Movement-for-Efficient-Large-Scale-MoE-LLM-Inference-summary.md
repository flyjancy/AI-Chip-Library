# 深度分析：《Patterns behind Chaos: Forecasting Data Movement for Efficient Large-Scale MoE LLM Inference》

## 基本信息

- **标题**：Patterns behind Chaos: Forecasting Data Movement for Efficient Large-Scale MoE LLM Inference
- **文档类型**：论文（arXiv 预印本，17 页）
- **作者**：Zhongkai Yu、Yue Guan、Zihao Yu（Indiana University Bloomington）、Chenyang Zhou（Columbia University）、Zhengding Hu、Shuyi Pei（Samsung）、Yangwook Kang（Samsung）、Yufei Ding、Po-An Tsai（NVIDIA）
- **机构**：UC San Diego、Indiana University Bloomington、Columbia University、Samsung Semiconductor、NVIDIA
- **发表 venue**：arXiv:2510.05497v5 [cs.DC]（2026-05-12 的 v5）
- **年份**：2026
- **链接**：https://arxiv.org/abs/2510.05497；**profiling trace 公开**于 `https://huggingface.co/datasets/core12345/MoE_expert_selection_trace`

## 一句话总结

> 这篇论文做了**第一份面向数据搬移的大规模 MoE 专家选择画像**：用 4 个 2025 年发布的 200B–1000B MoE 模型（DeepSeek-V3 671B、Llama4-Maverick-128E 402B、Qwen3-235B、Kimi K2 1000B）超过 **24,000 条请求**，从时间（层间 / token 间 / prefill-decode）与空间（单专家不均衡 / 专家对共激活）两个维度提炼出**六条洞察**，其中最有用的是**「用 prefill 阶段的数据预测 decode 阶段的专家选择」**；在模拟的晶圆级 GPU 上按洞察改动架构获 **6.6× 平均加速**，在真实 8×H100 上用 prefill 导向的专家放置获 **15.5% 的 MoE 计算加速**（作者自述 8-GPU 规模下这已是受上限约束的下界）。

## 研究动机与问题定义

- **要解决的核心问题**：大规模 MoE（200B+、100+ 专家）已成为开源前沿模型的主流形态，但**随机专家选择机制引入的数据搬移开销成为多单元服务系统的主导瓶颈**。
- **现有方法的不足**：如图 1 所示，**此前没有工作在规模化条件下系统研究这些模式**——早期研究只在一个或两个小 MoE、有限硬件上做画像，给出的是表面观察而非系统级洞察。参数规模与专家数量激增后出现的新数据搬移模式仍未被探索。论文特别声明自己是**首个对多个此前未被研究的 SOTA 模型做全面分析**的工作。
- **切入角度**：以**数据搬移为中心（data-movement-centric）**做画像，并把观察按两类关系组织：
  - **时间关系（temporal）**：层间（两个相邻层）、token 间（同一层相邻 token）、阶段间（prefill 与 decode）。
  - **空间关系（spatial）**：单专家的激活不均衡、专家对的共激活亲和性。
- 论文的自我定位很明确：**profiling 是主要贡献，两个案例研究是验证手段**。第 VII 节写道 "our profiling insights, which constitute the paper's primary contribution"。

## 核心方法

### 画像设置

- **模型**：DeepSeek-V3（671B）、Llama4-Maverick-128E（402B）、Qwen3-235B（235B）、Kimi K2（1000B）。
- **规模**：**超过 24,000 条请求**，覆盖多样负载；结果取平均。
- **trace 公开**：专家选择 trace 已发布在 HuggingFace。

### 六条洞察（论文的核心产出）

**时间关系支撑的三条**

**★ 洞察 1：Prefill 数据驱动的预测（Ob3）**
用 prefill 阶段收集到的专家选择信息来预测 **decode 阶段初期**的专家选择。依据是 prefill 与 decode 的专家对热力图分布相似：全部层的 **Spearman 相关系数 ρ ≥ 0.7**（图 6e/6f）。论文指出，这个跨阶段一致性使 **prefill 的信息可以指导 decode 的初始若干步，直到积累了足够的 decode 数据**。

**★ 洞察 2：跨层次的内存管理（Ob1, Ob2）**
利用 token 级与层级的**时间相关性**来预取或缓存专家。这不是"全部缓存"，而是按时间相关性有选择地管理——论文把它与 PIM 系统（含本地与远程 DRAM die）关联起来讨论。

**★ 洞察 3：感知专家放置的负载分配（Ob4, Ob5）**
把专家放置信息纳入任务分配，以获得更好的负载均衡。

**空间关系支撑的三条**

**★ 洞察 4：热门专家去中心化（Ob4）**
**复制或打散高频使用的专家**以平衡负载。依据是单专家激活极不均衡——**最热专家被选择的频率是平均值的 16 倍以上**。

**★ 洞察 5：专家对分离（Ob5）**
**把频繁共激活的专家对分到不同的计算单元**以最大化并行度。依据是共激活热力图中亮点概率是理论随机值的 **20–40 倍**，且**前 10% 的专家对贡献了总激活量的 60–80%**（强偏斜）。论文同时指出这条有代价：分离会引入跨单元通信，效果取决于系统拓扑与 batch size，需要在并行度收益与通信成本之间权衡。

**★ 洞察 6：负载感知的服务系统（Ob4）**
利用任务类型、语言等工作负载信息，在服务开始前做专家迁移。

### 三类时间关系的量化结果

**Ob1（层间相关）**：条件累积分布 $P(e_j \mid e_i)$ 中，**下一层候选的前 20% 已覆盖**：

| 模型 | 覆盖率 |
| --- | ---: |
| DeepSeek-V3 | 50% |
| Qwen3 | 65% |
| **Llama4** | **77%** |
| Kimi K2 | 56% |

模型间差异明显：**Llama4 的相关性最强，DeepSeek 最弱**（原因之一是 Llama4 在 MoE 层之间插入了稠密 FFN 层，论文把相邻 MoE 层按 N 与 N+2 配对）。

**Ob2（token 间相关）**：同样取下一 token 候选的前 20%，覆盖率为 **DeepSeek-V3 47%、Qwen3 62%、Llama4 80%、Kimi K2 53%**。所有模型都出现一个共同模式——**热力图上的亮对角线**，即相邻 token 倾向选择同一个专家；这个模式**主要出现在较高层（17 与 43），不出现在低层（1 与 3）**，且与模型无关。

**Ob3（prefill-decode 相关）**：stage 间的热力图分布相似，Spearman ρ ≥ 0.7。

### 空间关系的量化结果

**Ob4（单专家不均衡）**：
- 最热专家被选择频率是平均的 **16 倍以上**。
- **任务相关**：分析 MMLU 全部 57 个学科，横向亮线说明**某些专家与学科无关地持续热门**，而其余热门专家**因学科而显著不同**——即"部分重叠 + 部分区分"。
- **语言相关**：用 MMLU Pro 的中文版（题目相同、语言不同）对照，**虽然中英文各有 5–6 个持续热门的专家，但两者只有 2 个重叠**。这直接支撑洞察 6：任务特征（含语言）显著影响专家选择，使任务感知的服务系统成为可能。

**Ob5（专家对共激活）**：
- 热力图中的亮点对应概率是理论值 $\frac{2}{n(n-1)}$ 的 **20–40 倍**。
- **前 10% 的专家对贡献总激活量的 60–80%**。
- DeepSeek 的热力图中频繁激活的专家对**落在红线之间形成亮方块**——这反映了 DeepSeek 的路由限制（token 只路由到相邻节点以降低通信开销）。论文据此指出**把共激活的专家对分离**有平衡负载的潜力。
- Llama4 因每层只选一个专家而被排除在共激活分析之外。

## 实验与结果

### 案例一：晶圆级 GPU 架构设计（模拟）

**背景与动机（第 IV.A 节）**

- GPU 厂商越来越多采用多 chiplet 架构以突破单 die 限制：摩尔定律接近极限，且**单 die 尺寸受光罩尺寸约束（800–1,000 mm²）**；先进封装如 TSMC CoWoS、Samsung X-Cube、Intel EMIB。
- 现有编程模型的问题：**MIG 能分割多 die GPU，但在该模式下高速 D2D 链路被禁用**，导致跨 die 通信退回慢 10–100× 的 NVLink 或 PCIe，从而抵消多 die 封装的好处。因此把 MIG 式模型扩展到晶圆级 GPU 需要重构 D2D/C2C 控制器工作流与分布式 LLC，**短期内不可行**。
- 论文采用**类单 GPU 编程模型**（与 HDPAT、Hecton 同路）：把整片晶圆暴露为统一 GPU，完全对软件隐藏多 die 拓扑与数据放置。

**架构设计**

在类单 GPU 编程模型下做两处"最小改动"（图 10a，橙色高亮）：

1. **带多级、数据放置感知能力的命令处理器（Global CP）**：执行智能任务分配算法，考虑专家在各 die 上的放置与选择偏斜，动态分配任务以在最小化 D2D 流量的同时均衡负载。
2. **硬件管理的数据驱动预测器**：本地 HBM 缓存来自远程 die 的常用专家；轻量预测器分析选择模式估计未来需求，把预测的专家缓存在本地以减少 D2D 流量。

**关键数据结构**：
- **Global CP** 维护两个结构：**专家分布表**（记录每个专家的初始 die ID，以及用 n-bit 二进制码表示的分布状态——每一位表示该专家是否存在于对应 die）；**跨 token 热力图**（记录随时间的专家激活模式，为预测提供历史数据）。
- **PDU 预测表**：每个 die 上的 PDU 为每个专家保存两个字段——**`cp_en` 位**（该专家是否应被本地缓存，由 Global CP 计算并下发）与 **`is_local` 位**（该专家是否已缓存在本地 HBM）。

**内核启动工作流**：新内核启动 → Global CP 运行任务分配算法把 MoE 内核切成逐 die 的子内核并执行预测器生成复制指导（`cp_en`）→ 把子内核与预测信息下发给本地 CP → 本地 CP 向 SM 分配任务并配置 D2D 控制器的预测表 → 计算后本地 CP 收集专家复制统计并回报 Global CP 更新专家分布信息。论文提到该设计**支持最多 100 层、每层 512 专家**。

**结果**

| 策略 | 吞吐相对 baseline |
| --- | ---: |
| **Pred Only** | 3.0× |
| **Allo Only** | 6.3× |
| **Allo+Pred** | **6.63×** |

- **按模型**（Allo+Pred）：**DeepSeek 7.0×、Kimi 8.2×、Llama 7.3×、Qwen 4.1×**；四人平均约 **6.6×**。DeepSeek 与 Kimi 受益更大，因为它们专家数更多（**256 vs 128**）且选择模式更复杂。
- **按 chiplet 架构**：**Dojo 6.0×、TSMC 7.5×**（die 数相近，25 vs 24）。TSMC 的**矩形布局使 die 之间距离更远**，在不做策略性任务分配时引入更多跨单元通信，因此在我们策略下收益更大。
- **对比 EP**：在**小 batch（如 4096）时我们的策略与 EP 表现相近**——每个专家的 token 数少、执行是内存受限的，把一个专家拆到多个 die 没有收益，策略退化为 EP。**优势在大 batch 才出现：batch 16,384 时相对 EP 有 1.44× 加速**。
- **跳数下降（hop count = 所有跨单元通信的曼哈顿距离之和）**：

| 策略 | 跳数下降 | 对应性能提升 |
| --- | ---: | ---: |
| Pred Only | 4.5× | 3.0× |
| Allo Only | **142×** | 6.3× |
| Allo+Pred | **>213×** | 6.63× |

  论文对这三行的解读很关键：**Pred Only 的跳数下降（4.5×）与性能提升（3.0×）基本成比例**，说明 baseline 里跨单元通信是主导瓶颈；**Allo Only 的跳数下降 142× 远超性能提升 6.3×**，说明用上分配算法后跨单元通信不再是唯一瓶颈；**Allo+Pred 把跳数降了 213× 以上，但性能只提升 6.63×**，相对 Allo Only 仅平均提升 1.1×——即超过某个点之后，继续减少通信不再带来成比例的性能收益，瓶颈转移到了工作负载分配（workload distribution）。
- **DRAM 访问分解**：baseline 的多数读来自远程 die；Pred Only / Allo Only / Allo+Pred 都把大部分远程 DRAM 读转成了本地读。Allo+Pred 相对 Allo Only 进一步减少远程读，因为只有极热门专家才需要跨多 die 计算。
- **与基于 host CPU 的实现对比**：把分配算法放到 host CPU 上也可行但有更高开销。**Dojo 配置**下 host CPU 分配开销为 **DeepSeek V3 5.2%–6.4%**、**Qwen3 11.1%–14.2%**；**Dojo-Enhanced 配置**下升到 **DeepSeek V3 19.3%–23.8%**、**Qwen3 42.0%–51.6%**。Qwen3 开销更大的原因是每层 MoE 需要一次 CPU–GPU 的 PCIe 传输（CPU 需要 GPU 的专家分布表来跑分配器，结果又要传回 GPU），而 **Qwen3 的 MoE 层更多（94 vs 58）**且每层计算量更小，放大了传输的相对成本。

### 案例二：prefill 导向的 decode 专家放置（真实 GPU 集群）

**动机**：大规模 MoE 服务（200+ GPU）中负载不均衡是最大挑战之一。**EPLB** 通过动态调整专家放置来应对，但它**每 3000+ 步才触发一次**，且依赖周期性收集的画像数据。于是问题变成：**在还没有任何画像数据的初始约 1000 个 decode token 上，专家该怎么放？** 这对短输出请求尤其紧迫——EPLB 永远收集不到足够数据来起作用。洞察 1 给出答案：用 prefill 阶段的专家选择信息指导初始 decode 步的放置。

**设置**

- **Qwen3-235B 用 SGLang 部署在 8×H100 上**，NVLink 互连；**DeepEP** 作为 MoE 后端；`ep_dispatch_algorithm` 设为 "dynamic" 以使 token 在重复专家的副本间均匀分布。
- **度量口径**：**MoE 计算时间**——三个专家线性层，**排除 attention、all-to-all 与 top-k**。
- **数据**：MMLU 与 Global-MMLU；batch 从 64 到 16,384。
- **baseline 定义**（这一点很重要）：**Default** 是 Qwen 与 SGLang 使用的标准连续放置（专家 0–15 在 GPU-0、16–31 在 GPU-1，以此类推）；**Best 与 Worst 是用 oracle 的 decode 阶段选择生成的理论最优与最差放置，在实践中不可得**；**Remap 与 Dup 是论文的两个 prefill 导向策略**（Dup 每 GPU 多用一个槽位，得到每层 **128+8 = 136 个专家**）。

**结果（图 17）**

| Batch | Default | Worst | Best（oracle） | Remap（本文） | Dup（本文） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 4K | 1.00 | 0.80 | 1.33 | **1.25** | 1.28 |
| 8K | 1.00 | 0.56 | 1.20 | **1.22** | 1.20 |
| 16K | 1.00 | 0.51 | 1.14 | **1.11** | 1.12 |
| 24K | 1.00 | 0.57 | 1.04 | **1.04** | 1.04 |

- **Remap 与 Dup 相对 Default 的加速为 15.5% 与 12.5%**（这是四个 batch 点的算术平均，与图中 4K 处的 1.25× 一致），**相对 Worst 有 2× 以上加速**，且**都在 Best（oracle）的 10% 以内**。论文据此认为方法有效，因为 Best 使用的是实践中不可得的 oracle 信息。
- **作者主动限定了这个结果的上界**：**8-GPU 的 EP 规模本身就限制了可获得的改进**——EP8 下每个 GPU 持有 16 个专家/层，因此**每个 GPU 很可能已经同时含有热专家与冷专家，即使 Default 布局也相对均衡**，最坏/最好执行时间比只有约 **1.3×**。论文明确表示**在更大的 EP 规模下、负载不均衡更明显时，预期会看到更大的加速**。

## 局限性与未来方向

- **两个案例的证据强度差异很大，需要分开引用**：**案例一（6.6× 平均加速）是在模拟的晶圆级 GPU 架构上、并包含架构改动（Global CP、PDU 预测表、D2D 控制器扩展）得到的结果**，其模拟器虽用真实 8×H100 数据校验（图 13 覆盖 MoE 层与 P2P 传输两类测试），但仍是模拟 + 前瞻架构。**案例二（15.5%）在真实 8×H100 上测得**，但作者自己说明 8-GPU 规模限制了可获得的上限。因此"6.6×"与"15.5%"不能并列当作同等证据强度的结果。
- **案例二的加速幅度小于案例一，且作者给出了为什么**：EP8 下每 GPU 已有 16 个专家的混合，max/min 执行时间比仅约 1.3×，因此 15.5% 接近该规模下的理论上限。这也意味着**该结果不能外推到更大集群**（论文认为会更好，但没有测量）。
- **案例一的关键依赖是"预测器"的准确率与开销，而材料对这两点着墨较少**：PDU 预测表只给出 `cp_en` 与 `is_local` 两个字段与更新流程，**没有报告预测命中率、误预测的代价、预测表的大小或功耗**。图 12 的跳数下降 >213× 与性能提升 6.63× 之间的巨大落差也说明**瓶颈在通信之外**，但论文只把原因归为"workload distribution"而没有进一步分解。
- **案例一的 6.6× 强依赖于 Allo+Pred 的组合，而单独 Pred 只有 3.0×、单独 Allo 为 6.3×**：也就是说**大部分收益来自任务分配算法（Allo），预测器只带来 1.1× 的平均增量**。摘要中"lightweight architectural modifications ... yield a 6.6x average speedup"的表述容易被读成"架构改动带来 6.6×"，而实际分解是 Allo 6.3× + Pred ×1.1。
- **host CPU 开销的对比暴露了算法依赖通信的问题**：Dojo-Enhanced 下 Qwen3 的 host CPU 分配开销高达 **42.0%–51.6%**，论文把原因归为 Qwen3 的 MoE 层更多（94 vs 58）且每层计算更小，导致每层一次的 CPU–GPU 往返被放大。**这是把分配算法放在芯片外部就会遇到的具体障碍**，也是论文主张"放进 GPU 命令处理器"的直接依据。但这一页只给了开销百分比，没有给出 host CPU 方案下的净性能。
- **画像的覆盖面**：4 个模型都是 2025 年发布的 MoE，且**Llama4 因每层只选 1 个专家而被排除在 Ob5（专家对共激活）分析之外**；Ob5 只基于 DeepSeek 与 Qwen 两个模型。密度模型的对比仅在 MoE 内部，没有与稠密模型的数据搬移做对照。
- **未来方向**：论文明确指出其洞察**适用范围远超这两个案例**，可服务于多 GPU 集群（Multi-Node DGX、NVL72）、CXU/CPU 内存分级（disaggregation）、flash 型多级内存系统、**PIM 架构（含本地与远程 DRAM die）**以及其他新兴平台（第 VII 节）。案例一还给出一个条件：**若未来的编程模型演进出多 GPU 式抽象、能对每个 die 做更细粒度控制，那么这些策略可以在系统层实现而不需任何架构改动**。

## 个人点评

- **这份工作的最大价值是那张公开的 trace 与六条洞察的可用形态**。24,000+ 请求、4 个 200B–1000B 模型的专家选择数据被发布在 HuggingFace 上，这比论文的结论本身更持久——任何做 MoE 服务、互连或内存层级的人都可以直接在上面验证自己的假设。六条洞察的表述也很克制：每条都绑定一个具体的观察编号（Ob1–Ob5），并给出量化口径（"下一层候选前 20% 覆盖 50–77% 的条件概率质量"、"最热专家频率是平均的 16 倍以上"、"前 10% 专家对贡献 60–80% 激活量"），而不是笼统地说"专家选择有规律"。
- **洞察 1（用 prefill 预测 decode）是六条里最实用的一条**，因为它把一个时序观察变成了可操作的工程手段：prefill 与 decode 的热力图 Spearman ρ ≥ 0.7，而 EPLB 需要 3000+ 步才能起作用——于是短输出请求永远等不到画像数据。案例二正是把这条变成了 prefill-guided placement，并在真实 H100 上拿到 15.5%。作者同时诚实地说明了 8-GPU 规模下 max/min 执行时间比仅约 1.3×，所以 15.5% 已是该规模下的接近上限——**这种主动限定自己结果范围的写法，比报一个漂亮的倍数更有用**。
- **案例一的跳数分析是全文分析质量最高的一段**。三组数字（Pred Only 跳数 4.5× / 性能 3.0×；Allo Only 跳数 142× / 性能 6.3×；Allo+Pred 跳数 >213× / 性能 6.63×）清晰地展示了一条非线性关系：**baseline 里通信是主导瓶颈，用上分配算法后通信不再是唯一瓶颈，继续压通信边际收益迅速衰减**。这比单说"我们降了 213× 跳数、快了 6.6×"信息量大得多，因为它指出了下一个瓶颈（workload distribution）的位置。
- **需要留意的三处口径**。第一，**6.6× 与 15.5% 的证据强度不同**（前者是模拟 + 前瞻架构 + 架构改动，后者是真实硬件），摘要里并列出现容易造成误会。第二，案例一的 6.6× 里 **Allo（任务分配）贡献 6.3×，Pred（预测器）只贡献 1.1×**，因此"lightweight architectural modifications yield 6.6x"这个表述需要更精确地读。第三，案例二的 **Best/Worst 是 oracle 生成的、实践中不可得**，所以"在 Best 的 10% 以内"是一个合理的自评方式，但不能理解为"已接近最优"。
- **一个具体的设计数字值得记住**：host CPU 跑分配算法时，**Dojo-Enhanced 下 Qwen3 的开销达 42.0%–51.6%**，原因是每层 MoE 需要一次 CPU–GPU 往返（取专家分布表、回传分配结果），而 Qwen3 有 94 个 MoE 层且每层计算量更小。这条把"分配算法该放在哪"从抽象讨论变成了可量化的工程约束：**任何每层都要与主机通信的放置策略，都会被层数与每层计算量的比值放大**。

## 工程化三问总结

### 1. 它解决了什么瓶颈？

- **应用场景与核心瓶颈**：大规模 MoE LLM 的多单元服务。瓶颈被明确定义为**专家随机选择引入的数据搬移开销**——它在多单元服务系统中成为主导瓶颈（摘要）。案例一的跳数分析进一步给出了瓶颈的动态位置：baseline 阶段是跨单元通信，用上任务分配后转移到工作负载分配。
- **现有方法为何不足**：**没有此前工作在规模化条件下系统研究这些模式**——早期研究只覆盖一两个小 MoE 与有限硬件，给出表面观察。另外 EPLB 虽做动态专家放置，但**每 3000+ 步才触发一次、依赖周期性画像**，因此对短输出请求无效（初始约 1000 个 decode token 完全没有数据）。MIG 式多 die 编程模型因**在该模式下禁用高速 D2D 链路**（退回慢 10–100× 的 NVLink/PCIe）而不适用于晶圆级 GPU。
- **论文证据的分层**：
  - **画像证据（论文自述为主要贡献）**：4 个模型的 24,000+ 请求专家选择 trace（公开）；Ob1–Ob5 的量化结果——层间前 20% 覆盖 50%/65%/77%/56%；token 间 47%/62%/80%/53%；stage 间 ρ ≥ 0.7；最热专家频率 16× 平均；专家对共激活 20–40× 理论值且前 10% 占 60–80% 激活量；MMLU 57 学科与中英文对照（中英热门专家仅 2 个重叠）。
  - **案例一（模拟 + 前瞻架构，需降级）**：Allo+Pred 相对 baseline 6.63×；按模型 DeepSeek 7.0×、Kimi 8.2×、Llama 7.3×、Qwen 4.1×；按架构 Dojo 6.0×、TSMC 7.5×；对比 EP 在 batch 16,384 时 1.44×；跳数下降 4.5×/142×/>213×；DRAM 访问由远程读转本地读；host CPU 开销 5.2%–6.4%（DeepSeek/Dojo）到 42.0%–51.6%（Qwen3/Dojo-Enhanced）。模拟器用真实 8×H100 数据校验（MoE 层与 P2P 两类测试）。
  - **案例二（真实硬件，但规模受限）**：Qwen3-235B + SGLang + 8×H100 + DeepEP；Remap/Dup 相对 Default 15.5%/12.5%，相对 Worst 2× 以上，在 oracle Best 的 10% 以内。**作者声明 8-GPU EP 规模下限定了改进上限（max/min 执行时间比仅约 1.3×）**。

### 2. 用了什么结构或方法？

- **画像方法**：以数据搬移为中心，按**时间维度**（层间 Ob1、token 间 Ob2、prefill-decode 间 Ob3）与**空间维度**（单专家不均衡 Ob4、专家对共激活 Ob5）分类，用条件概率累积分布与 Spearman 相关系数做量化，并做学科维度（MMLU 57 学科）与语言维度（中英文 MMLU Pro）的对照。
- **案例一的架构结构**：类单 GPU 编程模型（整片晶圆暴露为统一 GPU，隐藏多 die 拓扑）。两处最小架构改动：**Global CP**（多级、数据放置感知的任务分配）与**硬件管理的数据驱动预测器**。关键数据结构：Global CP 的**专家分布表**（n-bit 二进制码表示专家在哪些 die 上）与**跨 token 热力图**；每 die 的 **PDU 预测表**（`cp_en` 与 `is_local` 两位）。工作流为内核启动时 Global CP 切子内核并生成复制指导 → 下发本地 CP → 配置 D2D 控制器预测表 → 计算后回报更新时间。支持最多 100 层 × 512 专家。
- **案例二的软件结构**：SGLang + DeepEP，通过 `init_expert_location` 接口操纵专家放置，`ep_dispatch_algorithm = "dynamic"` 保证重复专家的副本间均匀分发；用插入 SGLang 的 `cuda.Event` 计时器逐 GPU 测量 attention/top-k/all-to-all/MoE 各阶段。
- **策略设计**：案例一是 Allo（感知放置的任务分配）+ Pred（跨 token 与层间的时间相关性预测）；案例二是 prefill-guided 的 Remap 与 Dup（Dup 每 GPU 加一个额外槽位，每层 128+8 = 136 专家）。
- **量化策略**：本材料不涉及数值量化，聚焦专家选择的离散决策模式。

### 3. 对芯片架构和 RTL 有什么启发？

- **芯片架构**：五条。第一，**MoE 的专家选择不是随机的，而是有时间与空间结构**——层间前 20% 候选覆盖 50–77% 的条件概率、token 间 47–80%、stage 间 ρ ≥ 0.7、最热专家频率 16× 平均、前 10% 专家对贡献 60–80% 激活量。任何面向 MoE 的加速器都可以把这些数字当作设计输入：如果预测有这般准确度，就不必为"随机访问全部专家"做最坏情况设计。第二，**"用 prefill 数据指导 decode"是一条可以在架构侧支持的机制**——把 prefill 阶段的专家选择统计暴露给放置决策，可以做成硬件可见的计数器/表，而不是软件事后统计。第三，**把放置与分配决策放进芯片内的命令处理器（Global CP）而非 host CPU，在每层都要通信的场景下是必要的**：案例二显示 host CPU 方案在 Qwen3/Dojo-Enhanced 上开销高达 42.0%–51.6%，而开销被 MoE 层数（94 vs 58）与每层计算量放大。这条对任何"每层都需重新决策"的调度机制都成立。第四，**预测/缓存表这类硬件的代价需要与收益一起评估**：论文的 PDU 预测表只带来 1.1× 的边际收益（Allo 6.3× → Allo+Pred 6.63×），而它需要 Global CP 的专家分布表、跨 token 热力图与每 die 的预测表；是否值得取决于表的大小与更新开销（论文未给）。第五，**多 die/晶圆级设计必须避免"退回低速互连"的编程模型空洞**：MIG 模式下禁用高速 D2D 使跨 die 通信慢 10–100×，直接抵消多 die 封装的好处——这是对多 die 架构定义编程模型时的直接警示。
- **RTL**：可落到实现层的模块包括：**Global CP 的任务分配与预测器执行单元**（需要支持按专家放置与选择偏斜做动态分配，并在内核启动时生成子内核与复制指导）；**专家分布表**（每专家一个 n-bit 二进制码，n 等于 die 数，因此需要 n 位宽的表项与位操作逻辑）；**跨 token 热力图存储**（记录随时间的激活模式，容量随层数与专家数增长，论文设计支持 100 层 × 512 专家）；**每 die 的 PDU 预测表中的 `cp_en`/`is_local` 两位及查表逻辑**；**D2D 控制器的预测表配置接口与本地 HBM 管理通路**；**本地 HBM 的专家缓存管理（替换/旁路）**；**专家复制统计的收集与回报通路**（本地 CP → Global CP）。上述模块的动机均来自论文描述，但**论文没有给出任何面积、功耗、时序或 SRAM 开销数据**；PDU 预测表的命中率与误预测代价也未报告。
- **推断边界**：第 1 问中画像证据（Ob1–Ob5 的量化值）与案例二的真实硬件结果属论文直接证据；案例一的 6.6× 与跳数下降属**模拟 + 前瞻架构**结果，需按此降级；第 2 问的结构描述全部来自论文。第 3 问的芯片架构与 RTL 内容为工程推断。论文中未提供的量值——预测命中率与误预测代价、预测表/热力图的容量与功耗、案例一模拟器的保真度细节、更大 EP 规模下的实际加速（论文仅预期更好）、以及案例一在真实晶圆级硅上的验证——均 `TBD`。
